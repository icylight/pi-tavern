# PiTavern 工作流实战：使用场景与问题模拟（用户视角 × Agent 视角）

> 本文把 PiTavern 群聊在**本仓库自身协作中的真实用法**当作产品用例：完整模拟一个任务从提出到收口的生命周期（用户视角 + agent 视角），记录每一步遇到的实际问题、当时的解法、以及问题对产品开发的指导。这是 dogfooding 记录——文档里每一个问题都有群聊实测出处（附 issue/序列号）。交互规范见 [interaction-model.md](./interaction-model.md)，协作规则见 [workflow.md](./workflow.md)。

## 1. 为什么要写这份文档

PiTavern 的设计目标是「多 agent 围绕用户协作」，而本项目自己就是最长的真实运行用例（PM/Dev/QA/Arch 四角色 + 用户，跨多个 issue 连续协作）。**工作流中暴露的问题 = 产品要解决的问题**：

- 消息打断、验证重复跑、发言配额不够、私聊倾向丢失、全员回应混乱、决策无归口……每一条都直接触发过产品/流程改动（#60/#64 聚合、§7 验证留痕、#46 发言上限、§3 私聊同步义务、v0.5 响应规则）。
- 新需求评审时先对照本文：这是哪个场景的哪个环节？用户/agent 在这里会碰到什么问题？

## 2. 视角模型

### 用户视角（User Persona / 创建者）

用户是节奏控制者：**开启讨论轮次、布置任务、观察进展、拍板决策、纠正方向**。用户期望：

1. 说一句话就能把任务派出去，agent 们围绕它协作，不需要用户重复解释
2. 群聊像「工作现场」：能看懂谁在做什么、卡在哪、结论是什么
3. 自己的倾向和指示能被所有 agent 收到并遵守（而不是只被私聊对象知道）
4. 进展快、不空转：同一件事不要被重复验证、重复询问
5. 随时能拍板：决策点清晰呈现，而不是淹没在讨论里

### Agent 视角（Character pi）

角色 agent 是执行者：**接收任务、讨论方案、产出、验证、汇报**。角色受这些约束：

1. 每轮发言有上限（roundMaxMessages），要挑「有增量」的话说
2. 只能通过 `tavern_speak` 公开发言；详细分析留在私有 session
3. 群聊消息在 run 边界**整批拉取到达**（#64 pull 模型：广播=标记、消费点拉全），运行中零注入、不假设逐条实时
4. 私聊（用户终端输入）不进群聊，需要主动转达
5. 有属主边界：文件、测试、文档各归其主，改动前要声明影响面

## 3. 完整场景模拟：一个任务的生命周期

以一个 bug 修复任务为例，八阶段走查。每阶段列出：用户做什么、agent 做什么、**实测遇到的问题**、当前解法。

### 阶段 0：任务提出（用户一句话）

- 用户：在创建者终端发一条消息（如「合并了,本地切换一下,然后修复消息同步的问题」）→ 开启新 Round
- agent：各角色读到群聊输入（环境批次 + 状态快照），判断是否与己相关

**实测问题**：
- 问题 0.1 全员回应乱：早期每个角色都回复用户，一条用户消息换来三份复读（User：「我在群里的聊天,你们都会回答我,这个有一点乱了」）→ 解法：唯一默认响应者 = PM，事实增量原则（workflow v0.5）
- 问题 0.2 用户消息不聚合：用户连发多条时每条触发一次投递（User 原始不满 → #60/#64 聚合方案）

### 阶段 1：归口与澄清（PM 回读）

- 用户：PM 一句话回读「做 X，落分支 Y，完成后 Z 算达标」，用户点头才开工
- PM：信息不足时列缺口追问（「待澄清问题 1/2/3」），不替技术拍板

**实测问题**：
- 问题 1.1 归口缺失：讨论结论不声明归属 → 反复对齐（如决策①版本号 495/500 交叉引用混乱）→ 解法：PM 声明「已归口 #xx」闭环
- 问题 1.2 私聊倾向同步时机：早期问题 = 私聊倾向丢失（User：「我的私聊倾向不同步」「所有人都要遵守这个」）→ 落地 §3 私聊同步义务；**随后 User 澄清时机问题**（「你们同步太早了,私聊的时候我还没和你们达成共识」）——私聊是讨论区，**未达共识的中间状态不转达**，达成共识后才同步群聊 + PM 归口。未同步视为未发生，过早同步同样视为无效（以共识版为准）

### 阶段 2：讨论收敛（四方讨论）

- 用户：等待方案，关键处拍板（如「这个 pr 上改」「按 pull 模型走」）
- agent：各角色从自己视角评估（Dev 实现形态 / Arch 架构裁决 / QA 测试面 / PM 范围），决策点汇总给用户

**实测问题**：
- 问题 2.1 消息交叉导致基准过期：A 角色通读后分支又前进，基准追不上（多次「消息交叉」）→ 解法：PM 每落盘 commit 群聊声明 hash；「同一状态只验证一次」
- 问题 2.2 决策点悬置：拍板项迟迟不决，开发阻塞（如 #64 决策① idle 触发时机讨论十几轮）→ 解法：PM 显式提请 + 汇总推荐意见；决策权始终归用户
- 问题 2.3 行号锚点漂移：评审评论定位（line 33）多方争论 → 解法：以「节标题」等稳定锚点表述

### 阶段 3：立项（issue + 分支）

- PM：讨论收敛 + 用户批准 → 开 issue（验收口径五要素）→ 指定分支名
- agent：无 issue 不干活（issue = 开工令）

**实测问题**：
- 问题 3.1 issue 编号冲突：issue 与 PR 共用编号空间（#60 bug issue vs PR 编号撞车）→ 解法：开 PR 前核对编号
- 问题 3.2 分支权限：Dev 自行 stash/建分支越权（User：「分支应该 pm 你操作」）→ 解法：git 写操作（含建分支/stash/merge/push）一律归 PM，不得委托
- 问题 3.3 分支未 rebase：PR 分支落后 main 导致 diff 混入已合并内容（User：「没 rebase」）→ 解法：开 PR 前核对 merge-base/树相等

### 阶段 4：实施（钉测先行）

- Dev：先写钉测（红）→ 实施 → 转绿；验证结果一行式留痕（命令 | 结果 | 锚@层 | 环境）
- QA：独立复核（不引用 Dev 自证），红钉有效性验证

**实测问题**：
- 问题 4.1 测试假红/假绿：环境变量漏注入导致静默失败（PITAVERN_TEST 裸跑假红）→ 解法：config 内联 env + 环境锚记录
- 问题 4.2 测试调真实 LLM：--no-env 时代 key 泄漏，每次 run 真实调用 DeepSeek（User：「测试需要接入 llm 吗?」）→ 解法：#52 env 白名单，测试确定性零 LLM
- 问题 4.3 行为契约修订无声明：改投递时机影响既有断言 → 解法：四方契约影响面声明 + acceptance.md 口径同步

### 阶段 5：评审与门禁

- Arch：diff 级评审（独立复核，不引用实现者自证）
- QA：按影响面跑门禁（unit + integration + 定向 acceptance），V0 格式留痕
- 原则：**引用不重跑**——同一状态只验证一次，main 验证 = 树相等核对 + 引用门禁证据

**实测问题**：
- 问题 5.1 重复验证：同一测试链跑 4 次（User：「验证这个你们会重复跑」）→ 解法：§7 验证阶梯 V0-V5（留痕即证据、引用不重跑、树相等核对）
- 问题 5.2 权威锚锚到脏树：验证跑在未提交工作区 → 解法：门禁前 git status + rev-parse HEAD，脏树不跑门禁

### 阶段 6：合并与收口

- 用户：合并 PR（唯一有合并权限的人）
- QA：main 验证（树相等 + 引用门禁证据 + User 实测）→ PM 关 issue（附收口证据评论）

**实测问题**：
- 问题 6.1 用户评论遗留未登记：PR 评论「太奇怪了」不阻塞但需跟进 → 解法：遗留项登记（#56/#57 语言审计），ADR 转正前必须完成
- 问题 6.2 语言风格：文档后端术语风（「无 DB 的事务对应物」）User 不满（「你们这块的说法遗留是后端的说法」）→ 解法：全文档语言审计（#57），白话优先原则

### 阶段 7：遗留与并行

- 遗留项登记（不阻塞当前，随里程碑强制完成）
- 并行工作流：新任务可在旧任务收口期间启动（分支隔离）

**实测问题**：
- 问题 7.1 发言配额耗尽：50 上限在密集讨论中不够（Dev 三次放行消息被吞，User：「看来 50 不够用」→ #46 改 100）
- 问题 7.2 工作区多分支堆积：合并后分支未清理（User：「本地的其他分支删除」「worktree 也删除」）→ 解法：分支清理纪律 + worktree 声明制度

## 6. 问题 → 产品开发指导（设计输入）

### 本文档对 #64 消息同步设计的指导（2026-08-02，PM+Arch+QA+Dev 四方映射）

- **设计目标溯源**：文档 U2 行「群聊输入必须整批聚合、零中间打断」= #64 pull 模型第一性目标（已入验收口径首句）
- **reload 交接面（场景 G）**：标记是派生状态（有新消息 ⟺ latest_sequence > 已见游标），**不落盘不交接**——游标已持久化（cursor-store），reload 后重 join 拉状态派生恢复；窗口定时器 ≤1s 瞬态可重置。验收断言：reload 期间到达的消息重 join 后组装拉全不丢不重
- **User 消息统一语义（场景 A）**：User 消息不特殊、同走标记通道；Round 开启由消费点识别新 User 消息完成，非投递时机职责
- **跨 Round 聚合消费（场景 A/F）**：组装契约 = 批内按游标序 + 快照 Round 以最新为准（拉取返回消息 + 状态快照，上下文组装时呈现）
- **非目标（场景 E 通道隔离）**：私聊（终端输入→单角色）不走群聊同步通道，隔离语义保持

### 待评估的产品改进候选（从问题反推）
1. **决策点聚合 UI**：把「待用户拍板」项在创建者界面汇总展示（阶段 2 的问题 2.2 直接来源）——用户不用翻讨论找决策点
2. **验证留痕工具化**：把「命令 | 结果 | 锚 | 环境」一行式做成扩展内命令（/tavern-note），替代手工贴（U4 的进一步产品化）
3. **reload 期间群聊状态展示**：热重载接管时创建者界面提示「扩展已重载，群聊延续」（场景 G reload 的可见性）
4. **发言配额预警**：接近上限时在群聊输入状态快照中带剩余次数（agent 可自行决定是否省话），减少中途静音（A2）
5. **分支/PR 关联展示**：`/tavern-status` 扩展显示当前任务分支与 issue 状态（阶段 3 的 3.2/3.3 直接来源）
