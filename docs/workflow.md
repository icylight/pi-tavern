# PiTavern 工作流规范（Workflow）

> 目的：减少任务布置分歧、杜绝 main 直接改动，统一四方（PM/Dev/QA/Arch）协作节奏。
> 属主：PM。变更须群聊声明影响面。
> 版本：v0.4（2026-08-02，User 指示「验证不要重复跑」→ 新增 §7 验证留痕与分级验证；v0.3 内容不变）

## 1. 任务布置：Task Brief 五要素

**issue 写入时机（2026-08-02 User 指示）**：讨论好了才写 GitHub issue——需求提出后先**本地临时记录**（PM 私聊整理，不写 GitHub、不动仓库），四方讨论收敛 + **User 批准后**才创建 issue，然后进入布置/执行流程；**无 issue 不干活**（issue 是开工令）。整体流程：**讨论收敛 → User 批准 → 开 issue → 分支开发 → 开 PR → User 合并**。issue 状态与任务状态同步流转（见第 6 节），**关闭 issue 前置条件：QA 在 main 验证通过（树相等核对 + 引用 PR 门禁证据 + User 实测）+ User 确认**。**验证环境：User 负责将本机 pi 更新为最新 pi-tavern**（真实环境验证），QA 在更新后的环境执行验证（按 §7 验证阶梯，不重跑全链）。

User 自然表达指示 → **PM 负责转译成 Task Brief 并回读确认**（User 不填模板）。每项任务必须齐备：

1. **目标与范围**：做什么 + 明确不做什么（边界，如"其他不动"）
2. **落点约束**：分支名（**PM 指定，跟随要开发的 issue**）；main 默认不动，例外须 User 明示
3. **验收锚点**：引用验收清单条目号（如 A1-A6 / U1-U4）；**无条目号的任务须先建条目再布置**（防口径漂移）
4. **执行人 / 评审人 / 验收人**：谁主做、谁评审、谁验收
5. **依赖顺序**：前置条件与后置动作

## 2. 分支纪律（最高优先级）

- **main 是受保护基线**：任何角色一律不在 main 上直接提交、推送、改动；main 保持与 origin/main 一致（验证：`git rev-parse main origin/main`）
- **分支由 PM 控制（2026-08-02 User 指示）**：分支分配跟随要开发的 issue——一个 issue/批次一个分支，PM 在 Task Brief 中指定分支名，User 确认；其他角色不自行开新分支，分支归属争议由 PM 裁决
- **推送分支须 User 审批**（2026-08-02 User 指示）：任何 `git push`（含工作分支推送、PR 分支）一律不得自主执行——先在群聊声明推送内容与目标分支，User 审批通过后才可推送；未审批的推送视为违规
- 所有改动落工作分支（`feat/*`、`fix/*`）；角色卡、docs、scripts 等一切文件改动同样遵守——**无例外**
- 分支从 main 切出（`git checkout -b feat/xxx main`），逻辑独立、一个任务一条分支（或按 User 指示并入既有分支）
- 分支合入 main 由 **User 亲自执行**（2026-08-01 指示），角色侧止于评审通过 + 证据齐备 + 宣布就绪
- **开发完成开 PR（PM 负责推送与 PR 创建/更新，2026-08-02 User 指示）**：PR 标题/描述引用 issue 编号，附 Task Brief 五要素 + 验收证据（命令 + 结果）；评审（Arch）与验收（QA）在 PR 上留痕；角色侧一律不执行 merge，PR 就绪后宣布，由 User 合并
- **git 写操作统一归 PM（2026-08-02 User 指示）**：迁分支、commit（落盘）、push、PR 创建/更新/评论、issue 操作一律由 PM 执行；Dev/QA/Arch 只产出属主范围内文件改动到工作区（commit 内容属主=各角色），不执行任何 git 写操作；git 只读（status/log/diff）保留用于排查
- 动手前先 `git status` + `git branch --show-current`：确认所在分支正确、工作区无他人未提交改动

## 3. 沟通与确认闭环

### 私聊-批准-同步（2026-08-02 User 指示）
- 需求澄清、方案讨论类 → **PM 与 User 私聊**；收敛成结论后，**User 批准才同步群聊**
- 群聊 = 讨论现场（User 可看）；issue 评论区 = 可靠结论载体；两者承载不同职责

### Issue 同步策略（2026-08-02 User 指示）
- User 新提出的 issue **不一定要在群里同步**；
- User 明确要求同步 / 不同步时，按指示执行；未明确时由 PM 按场景与相关度自行判断，**倾向不同步**；
- 判断参考：纯登记（无排期、不涉及他方动作、不影响当前序列、无契约面变更）→ 不同步，细节留在 issue；影响优先级、需成员行动、阻断当前工作、触碰契约面 → 同步（一句话说明 + issue 链接）；
- 同步形式从简：结论与细节放 issue 评论区，群聊只发摘要。

### 三句确认闭环（防错位核心）

1. **布置确认**：User 指示 → PM 一句话回读「做 X，落分支 Y，不动 main，完成后 Z 算达标」→ User 点头才开工
2. **执行确认**：执行人（Dev/QA）收到 Task Brief → 一句话复述理解 → 无歧义再动手；有歧义当场问，不猜测（ISSUE-003 教训）
3. **完成确认**：完成汇报附证据（命令 + 结果）→ 验收人按条目号验收 → 宣布就绪

## 4. 信息流与对齐（v0.3，2026-08-02 User 批准）

### 信息流拓扑：PM → Arch/QA → Dev（两阶段并行）

```text
阶段一：PM 派发需求 → Arch 出架构设计（文档形式）∥ QA 出文档级测试用例
        PM 评审（并行不阻塞：Arch/QA 不等评审结果直接进阶段二）
阶段二：Arch 写 UT（单元测试）∥ QA 写红测（集成/验收测试）
        Arch ↔ QA 互评（需求对齐；不是 Dev 开工条件）
触发：任一方测试完成 → Dev 开工
开工后：Dev 以 PM 需求为准，自主思考实现；与 Arch/QA 有分歧 → 继续对齐交互
```

- **单元测试属主 = Arch**（User 指示：单元测试可以让架构师写）
- 对齐目的：前期三次对齐（PM↔Arch、PM↔QA、Arch↔QA）让 Dev 拿到的输入收敛

### 对齐交互：三次握手（固定 3 条消息，无快速通道）

```text
SYN      发起方 → 对方：提出分歧/新信息
SYN-ACK  对方 → 发起方：响应理解 + 己方立场（双向，不限顺序）
ACK      确认达成一致 → 对齐完成
```

- 谁发起，向谁握手（方向由发起方决定）；有分歧就握手，无快速通道（通道会被滥用）

### 交付交互：四次挥手（固定 4 条消息，无快速通道）

```text
FIN  执行方 → 验收方：完成声明 + 证据
ACK  验收方 → 执行方：收到证据
FIN  验收方 → 执行方：验收结论（通过/有问题）
ACK  执行方 → 验收方：确认 → 交付关闭
```

- 谁交付，向谁挥手（方向由发起方决定）
- **粒度：仅可验收节点走挥手**（有验收人、有验收条目）；中间产物（commit、草稿、临时适配）不算交付，靠群聊正常流转

### 分歧裁决线（2026-08-02 User 批准）

- **文档/需求分歧 → PM 裁决**；**技术/契约分歧 → Arch 裁决**
- Arch 的架构产出必须以文档形式提交 PM 裁决
- 实现落地触发的既有测试适配：**Arch + PM 裁决，QA/Dev 提供意见**
- 裁决记录：本地文档（按记录要求存），不直接写 GitHub

## 5. 分歧仲裁

| 争议类型 | 仲裁者 | 依据 |
| --- | --- | --- |
| 范围之争 | PM | docs/acceptance.md、docs/implementation-plan.md |
| 契约之争 | Arch | docs/ 契约文档 + docs/adr/ |
| 质量之争 | QA | 可复现证据（最小步骤 + 期望/实际差异） |
| 执行落点之争 | User | User 指示优先（默认分支、main 不动） |

## 6. 默认值（减少往返）

- 默认落点：PM 指定分支（跟随 issue）；main 不动
- 默认只读：讨论阶段不写文件、不写 issue（本地临时记录）
- 默认范围：User 没提的不做；"其他不动"严格执行
- 默认署名：无需强制【角色名】开头（2026-08-02 User 指示）
- 默认提交：一个逻辑一个 commit；各角色产出属主文件改动到工作区（不自行 git add/commit），由 PM 统一检查并落盘；禁 `git add -A`

## 7. 任务状态流转与汇报

讨论收敛 → User 批准 → 开 issue（PM）→ 布置 → 回读确认 → 分支开发 → 开 PR（附五要素 + 验收证据）→ 评审/验收（Arch/QA，PR 留痕；按验证阶梯引用证据，不重跑全链）→ User 合并 → **QA 在 main 验证（树相等核对 + 引用 PR 门禁证据，不重跑全量；命令 + 结果留痕；User 已更新本机 pi 至最新 pi-tavern 并实测）** → 关闭 issue（main 验证通过 + User 确认）

**状态汇报归 PM（2026-08-02 User 指示）**：PM 向 User 汇报任务状态（卡点、等谁、下一步）；其他角色通过群聊与 PM 对接，不直接向 User 汇报；User 可看群聊讨论。状态在群聊声明 + issue 评论区登记（PM 属主，状态变更须群聊确认）。

### 验证留痕与分级验证（v0.4，2026-08-02 User 指示：验证不要重复跑）

**核心原则：同一状态（同 hash + 同层 + 同套件）只验证一次；留痕即证据，引用不重跑。**

- **V0 证据格式**：每次测试运行在 PR/issue 评论区留痕一行「命令 | 结果摘要 | hash@层」（层 = unit / integration / acceptance / 全量）；未留痕视为未发生；引用写「引用 <hash> 证据」。
- **V1 分级验证阶梯**（非全链默认）：
  - 红测链（QA）：只跑新增/受影响测试文件证红
  - Dev 自测：受影响层 + 红测转绿目标文件
  - 评审（Arch/QA）：diff 审查 + 只跑被改动文件的 unit 抽查，不重跑全链
  - 全量 test:qa 唯一跑点 = **PR 门禁**：QA 在 PR 分支头跑一次，即该树唯一全量证据
- **V2 双因子重跑判定**：重跑触发 = ① 涉及文件变更（src/test/docs）→ 重跑受影响层；或 ② 影响面声明——**实现者随证据链自带「影响面」字段**：受影响层小枚举（unit / acceptance-定向(附用例名) / 全链）+ 一句理由（如「改动拉取等待窗口 → 须重跑 live-delivery」）。**QA 判定 = 实现者声明 + 只读 diff 交叉核对**（重点扫异步/定时/超时/轮询类改动，秒级成本；声明是断言非证明）。声明与 diff 不符时才要求补跑；无触发 → 引用旧证据。
- **V3 证据复用与树相等**：同 hash 直接引用；main 验证 = `git rev-parse main^{tree} == PR头^{tree}` 树相等核对 + 引用 PR 门禁证据 + User 实测（真实环境），不重跑全量；树不等（合并冲突解决）才重跑受影响层。
- **V4 红/绿状态区分**：QA 证红与 Dev 证绿是不同状态，各跑一次不算重复；重复指同状态同层同套件多次运行。
- **V5 与 #45 分工**：本规则消「重复跑」（次数维度）；#45 优化单次成本（耗时/CPU），排期不受本规则影响。

## 8. 生效与修订

- 四方确认 + User 批准后生效
- 修订：群聊提议 → 四方确认 → PM 更新本文档（落分支提交）
