# PiTavern 工作流规范（Workflow）

> 目的：减少任务布置分歧、杜绝 main 直接改动，统一四方（PM/Dev/QA/Arch）协作节奏。
> 属主：PM。变更须群聊声明影响面。
> 版本：v1.2（2026-08-02，教训：PR-B 中间态 37d1b74 落盘后 integration 52 红不可锚——unit 绿不覆盖 WS 集成面 → §7.5 补预跑窗口；v1.1 内容不变）

## 1. 任务布置：Task Brief 五要素

**issue 写入时机（2026-08-02 User 指示）**：讨论好了才写 GitHub issue——需求提出后先**本地临时记录**（PM 私聊整理，不写 GitHub、不动仓库），四方讨论收敛 + **User 批准后**才创建 issue，然后进入布置/执行流程；**无 issue 不干活**（issue 是开工令）。整体流程：**讨论收敛 → User 批准 → 开 issue → 分支开发 → 开 PR → User 合并**。issue 状态与任务状态同步流转（见第 6 节），**关闭 issue 前置条件：QA 在 main 验证通过（树相等核对 + 引用 PR 门禁证据 + User 实测）+ User 确认**。**验证环境：User 负责将本机 pi 更新为最新 pi-tavern**（真实环境验证），QA 在更新后的环境执行验证（按 §7 验证阶梯，不重跑全链）。

User 自然表达指示 → **PM 负责转译成 Task Brief 并回读确认**（User 不填模板）。每项任务必须齐备：

1. **目标与范围**：做什么 + 明确不做什么（边界，如"其他不动"）
2. **落点约束**：分支名（**PM 指定，跟随要开发的 issue**）；main 默认不动，例外须 User 明示
3. **验收锚点**：引用验收清单条目号（如 A1-A6 / U1-U4）；**无条目号的任务须先建条目再布置**（防口径漂移）
4. **执行人 / 评审人 / 验收人**：谁主做、谁评审、谁验收
5. **依赖顺序**：前置条件与后置动作

## 2. 分支纪律（最高优先级）

- **main 是受保护基线**：任何角色一律不在 main 上直接提交、推送、改动；main 保持与 origin/main 一致（验证：`git rev-parse main origin/main`）
- **分支由 PM 控制（2026-08-02 User 指示）**：分支分配跟随要开发的 issue——一个 issue/批次一个分支，PM 在 Task Brief 中指定分支名，User 确认；其他角色不自行开新分支，分支归属争议由 PM 裁决
- **推送分支须 User 审批**（2026-08-02 User 指示）：任何 `git push`（含工作分支推送、PR 分支）一律不得自主执行——先在群聊声明推送内容与目标分支，User 审批通过后才可推送；未审批的推送视为违规
- 所有改动落工作分支（`feat/*`、`fix/*`）；角色卡、docs、scripts 等一切文件改动同样遵守——**无例外**
- 分支从 main 切出（`git checkout -b feat/xxx main`），逻辑独立、一个任务一条分支（或按 User 指示并入既有分支）
- 分支合入 main 由 **User 亲自执行**（2026-08-01 指示），角色侧止于评审通过 + 证据齐备 + 宣布就绪
- **worktree 纪律（v0.5 补充，2026-08-02 User 指示）**：默认单 worktree——评审/开发一律在主仓库分支内做，不建额外 worktree；worktree 仅例外使用（并发任务需隔离运行时），创建前须 PM 同意 + 群聊声明（属主/任务/目录）+ 记入 issue，未声明的 worktree 一律视为违规（#49 后清理时逐层确认的根因即两个 worktree 从未声明）；生命周期：任务收口随分支清理一并移除，不留未声明旁支
- **开发完成开 PR（PM 负责推送与 PR 创建/更新，2026-08-02 User 指示）**：PR 标题/描述引用 issue 编号，附 Task Brief 五要素 + 验收证据（命令 + 结果）；评审（Arch）与验收（QA）在 PR 上留痕；角色侧一律不执行 merge，PR 就绪后宣布，由 User 合并
- **变更记录（CHANGELOG，2026-08-02 User 指示）**：`CHANGELOG.md` 由 PM 归口维护（生成 + 更新，其他角色不提改）。每里程碑 / 显著 PR 合入后，PM 随合入批次同步更新（Keep a Changelog 格式 + 语义化版本；条目面向用户影响，不倾倒 git log）；PR 描述如需 changelog 条目，由 PM 在 Task Brief 中说明
- **git 写操作统一归 PM（2026-08-02 User 指示）**：git add/commit、迁分支、分支创建/切换/删除、stash/apply、merge/rebase、push、PR 创建/更新/评论、issue 操作一律由 PM 统一执行，**不得委托**。任何角色不得以「拆分自己的工作区改动」「恢复现场」等理由自行执行 git 写操作——需要拆分支/暂存时，先声明工作区内容归属（「工作区 = X 改动集」），由 PM 执行拆分；commit 内容属主=各角色；git 只读（status/log/diff/fetch）保留用于排查
- 动手前先 `git status` + `git branch --show-current`：确认所在分支正确、工作区无他人未提交改动

## 3. 沟通与确认闭环

### 私聊-批准-同步（2026-08-02 User 指示）
- 需求澄清、方案讨论类 → **PM 与 User 私聊**；收敛成结论后，**User 批准才同步群聊**
- 群聊 = 讨论现场（User 可看）；issue 评论区 = 可靠结论载体；两者承载不同职责

### 私聊同步义务（2026-08-02 User 指示：私聊倾向不同步，所有人都要遵守）
- **事实前提**：User 与任一角色的私聊内容（决策倾向/指示/新事实/意见）**默认不会自动进入群聊**，其他角色不可见
- **同步义务**：任何角色与 User 私聊，凡涉及决策倾向/指示/新事实，**达成共识后**主动同步到群聊（内容摘要 + 状态标注），交 PM 归口记录，不留私聊盲区
- **同步时机（2026-08-02 User 澄清：同步太早了）**：私聊是讨论区，**未达共识的中间讨论不转达**；过早同步会误导群聊——达成共识后才同步；未同步视为未发生，**过早同步同样视为无效（以共识版为准）**

### Issue 同步策略（2026-08-02 User 指示）
- User 新提出的 issue **不一定要在群里同步**；
- User 明确要求同步 / 不同步时，按指示执行；未明确时由 PM 按场景与相关度自行判断，**倾向不同步**；
- 判断参考：纯登记（无排期、不涉及他方动作、不影响当前序列、无契约面变更）→ 不同步，细节留在 issue；影响优先级、需成员行动、阻断当前工作、触碰契约面 → 同步（一句话说明 + issue 链接）；
- 同步形式从简：结论与细节放 issue 评论区，群聊只发摘要。

### User 消息响应规则（v0.5，2026-08-02 User 指示：群里聊天全员回应有点乱）

- **唯一默认响应者 = PM**：User 群聊发言 → 仅 PM 回应（回读/确认/提问/汇报）；PM 点名或议题明确属主时对应角色才答
- **事实增量原则**：同议题一方已答，他方只补新事实（新核验/纠错/新承诺）；纯附和/复读/重复确认一律不发——§7「同一状态只验证一次」在对话层的延伸（同一消息只应答一次）
- **交叉消息免补发**：消息交叉导致的重复状态以最新文件/分支状态为准，不再补发对齐（本轮多次交叉补发全属此类）
- **角色间讨论不受限**：非 User 消息的四方协作维持现状
- 汇报口径不变：PM 为唯一对 User 汇报点

### 三句确认闭环（防错位核心）

1. **布置确认**：User 指示 → PM 一句话回读「做 X，落分支 Y，不动 main，完成后 Z 算达标」→ User 点头才开工
2. **执行确认**：执行人（Dev/QA）收到 Task Brief → 一句话复述理解 → 无歧义再动手；有歧义当场问，不猜测（ISSUE-003 教训）
3. **完成确认**：完成汇报附证据（命令 + 结果）→ 验收人按条目号验收 → 宣布就绪

## 4. 信息流与对齐（v0.3，2026-08-02 User 批准）

### 信息流拓扑：PM → Arch/QA → Dev（两阶段并行）

```text
阶段一：PM 派发需求 → Arch 出架构设计（文档形式）∥ QA 出文档级测试用例
        PM 评审（并行不阻塞：Arch/QA 不等评审结果直接进阶段二）
阶段二：Arch 写 UT（单元测试）∥ QA 写红测（集成/验收测试）
        Arch ↔ QA 互评（需求对齐；不是 Dev 开工条件）
触发：任一方测试完成 → Dev 开工
开工后：Dev 以 PM 需求为准，自主思考实现；与 Arch/QA 有分歧 → 继续对齐交互
```

- **单元测试属主 = Arch**（User 指示：单元测试可以让架构师写）
- 对齐目的：前期三次对齐（PM↔Arch、PM↔QA、Arch↔QA）让 Dev 拿到的输入收敛

### 对齐交互：三次握手（固定 3 条消息，无快速通道）

```text
SYN      发起方 → 对方：提出分歧/新信息
SYN-ACK  对方 → 发起方：响应理解 + 己方立场（双向，不限顺序）
ACK      确认达成一致 → 对齐完成
```

- 谁发起，向谁握手（方向由发起方决定）；有分歧就握手，无快速通道（通道会被滥用）

### 交付交互：四次挥手（固定 4 条消息，无快速通道）

```text
FIN  执行方 → 验收方：完成声明 + 证据
ACK  验收方 → 执行方：收到证据
FIN  验收方 → 执行方：验收结论（通过/有问题）
ACK  执行方 → 验收方：确认 → 交付关闭
```

- 谁交付，向谁挥手（方向由发起方决定）
- **粒度：仅可验收节点走挥手**（有验收人、有验收条目）；中间产物（commit、草稿、临时适配）不算交付，靠群聊正常流转

### 分歧裁决线（2026-08-02 User 批准）

- **文档/需求分歧 → PM 裁决**；**技术/契约分歧 → Arch 裁决**
- Arch 的架构产出必须以文档形式提交 PM 裁决
- 实现落地触发的既有测试适配：**Arch + PM 裁决，QA/Dev 提供意见**
- 裁决记录：本地文档（按记录要求存），不直接写 GitHub

## 5. 分歧仲裁

| 争议类型 | 仲裁者 | 依据 |
| --- | --- | --- |
| 范围之争 | PM | docs/acceptance.md、docs/implementation-plan.md |
| 契约之争 | Arch | docs/ 契约文档 + docs/adr/ |
| 质量之争 | QA | 可复现证据（最小步骤 + 期望/实际差异） |
| 执行落点之争 | User | User 指示优先（默认分支、main 不动） |

## 6. 默认值（减少往返）

- 默认落点：PM 指定分支（跟随 issue）；main 不动
- 默认只读：讨论阶段不写文件、不写 issue（本地临时记录）
- 默认范围：User 没提的不做；"其他不动"严格执行
- 默认署名：无需强制【角色名】开头（2026-08-02 User 指示）
- 默认提交：一个逻辑一个 commit；各角色产出属主文件改动到工作区（不自行 git add/commit），由 PM 统一检查并落盘；禁 `git add -A`

## 7. 任务状态流转与汇报

讨论收敛 → User 批准 → 开 issue（PM）→ 布置 → 回读确认 → 分支开发 → 开 PR（附五要素 + 验收证据）→ 评审/验收（Arch/QA，PR 留痕；按验证阶梯引用证据，不重跑全链）→ User 合并 → **QA 在 main 验证（树相等核对 + 引用 PR 门禁证据，不重跑全量；命令 + 结果留痕；User 已更新本机 pi 至最新 pi-tavern 并实测）** → 关闭 issue（main 验证通过 + User 确认）

**状态汇报归 PM（2026-08-02 User 指示）**：PM 向 User 汇报任务状态（卡点、等谁、下一步）；其他角色通过群聊与 PM 对接，不直接向 User 汇报；User 可看群聊讨论。状态在群聊声明 + issue 评论区登记（PM 属主，状态变更须群聊确认）。

### 验证留痕与分级验证（v0.4→v0.6，2026-08-02 User 指示：验证不要重复跑；**v0.6 超驰注记：门禁改分层压缩默认定向、全量 test:qa 按需触发——见 V1 触发条件 ①-④**，本节其余 v0.4 内容不变）

**核心原则：同一状态（同 hash + 同层 + 同套件）只验证一次；留痕即证据，引用不重跑。**

- **V0 证据格式与四级锚定**：每次测试运行在 PR/issue 评论区留痕一行「命令 | 结果摘要 | hash@层 | 环境」（层 = unit / integration / acceptance / 全量；环境分两类锚，不可混用——① 验收门禁锚 = references/pi@子模块 commit + node 版本（acceptance 经 pi-test.sh 驱动子模块内真实 pi，当前 5bc1c2c0）；② 真实环境锚 = 全局 pi 版本 + node（User 实测 / main 验证）。acceptance 证据必须含门禁锚；跨类引用 = 环境漂移 → 重跑受影响层；references/pi 子模块升级（User 日常更新）即触发；子模块 pin 与全局版本的已知差异属 Dev/PM 协调项）；未留痕视为未发生；引用写「引用 <hash> 证据」。hash 锚定分四级：
  - ① 自测/红测（常含未提交改动，PM 落盘前）：标注「含未提交改动，基线 HEAD=<hash>」——仅参考/测试有效性证明（证明测试钉住缺陷），不作权威证据、不可引用
  - ② 权威锚 = PR 门禁分支头（committed tree）：QA 在分支头跑门禁那一刻的树（默认定向、按需全量，见 V1），是唯一可引用锚；跑启动时记 HEAD，运行中分支头前进则该证据对新头过期——补跑或标注 delta
  - ③ 同树引用：已提交树上的绿跑（main 验证树相等核对）可直接引用
  - ④ 变更重跑触发：分支新提交 / 环境漂移 → 重跑受影响层后再锚
  - 脏工作区陷阱：HEAD 不含被测内容时禁止裸引用 hash（会锚到错误树 = 引用无效证据，恰是本规则要根除的）
- **V1 分级验证阶梯**（非全链默认）：
  - 红测链（QA）：只跑新增/受影响测试文件证红，留痕标注失败阶段（哪个 waitFor/断言、多少秒超时），Dev 据此直指修复点，避免二次排查；红测定位 = 测试有效性证明，非权威证据（V0-①）
  - Dev 自测（2026-08-02 User 指示分工：**Dev 跑单元测试，QA 跑集成测试及以上**）：unit 受影响层 + 红测转绿目标文件（unit 域）；证绿时反向引用对应红测（「对应 QA 红测 <hash> 失败阶段 X，已修复，现绿」+ 修复点文件/机制），红绿两行证据互相锚定，评审一眼看出红在何处/改在何处/为何转绿。**Dev 不跑 integration/acceptance 全量**（集成/验收层证据 = QA 域，Dev 多跑 = 重复根源之一）；Dev 需要集成层行为确认时声明由 QA 执行或等验收
  - 评审（Arch/QA）：diff 审查 + 只跑被改动文件的 unit 抽查，不重跑全链。**评审线（2026-08-02 User 指示：Arch 承担 code review）**：Arch = 架构/契约评审 + **代码评审**（代码正确性、边界与错误处理、命名与可读性、测试充分性——对 Dev 每步落盘 commit 与 PR 终态均适用）；QA = 测试质量与验收证据评审（断言覆盖、红绿锚定、验收口径）。Dev 响应评审意见（L42 GitHub 分工），评审意见由 PM 归口发布到 PR/issue
  - **默认门禁 = 分层压缩（v0.6，2026-08-02 User 指示：不默认全量，QA 只跑改动的，等需要时跑全量）**：unit 全量 + integration 全量（秒级 ~13s，成本可忽略不裁）+ acceptance **只跑受影响文件**（定向，范围按 V2 影响面判定）。**全量 test:qa 按需触发**，触发条件（任一）：① 契约面变更（协议/持久化/schema/ADR，影响面声明=全链）② User 要求 ③ QA 判定（声明与 diff 交叉核对后影响面扩散超出定向能力，或周期性校准防盲区累积——如每 5 个 PR 择机一次）④ 关闭 issue 收口时 QA 判定需要。门禁执行细节：跑前 `git status` + `git rev-parse HEAD` 确认分支头且工作区干净（脏树不跑门禁，杜绝权威锚锚到脏树）；定向跑留痕附受影响文件清单 + HEAD^{tree}，全量跑留痕同 V0。Dev 协调承诺：QA 宣布跑门禁时 Dev 不产出新改动；在途产出先交 PM 落盘或明示 QA 延后门禁
- **V2 双因子重跑判定**：重跑触发 = ① 涉及文件变更（src/test/docs）→ 重跑受影响层；或 ② 影响面声明——**实现者随证据链自带「影响面」字段**：受影响层小枚举（unit / acceptance-定向(附用例名) / 全链）+ 一句理由（如「改动拉取等待窗口 → 须重跑 live-delivery」）。**QA 判定 = 实现者声明 + 只读 diff 交叉核对**（重点扫异步/定时/超时/轮询类改动，秒级成本；声明是断言非证明）。声明与 diff 不符时才要求补跑；无触发 → 引用旧证据。
- **V3 证据复用与树相等**：同 hash 直接引用；main 验证 = `git rev-parse main^{tree} == PR头^{tree}` 树相等核对 + 引用 PR 门禁证据 + User 实测（真实环境），不重跑全量；树不等（合并冲突解决）才重跑受影响层。树相等只证内容相同、不证环境相同——引用时对照证据行环境上下文（pi 版本号），环境漂移则重跑受影响层。**逐 PR 验收同规则（2026-08-02 User 批评「重复跑测试」后补充）**：QA 逐 PR 验收 = 树相等核对（HEAD^{tree} == 实现者证据对应 tree）+ 引用实现者证据 + 仅新增/受影响用例定向抽查；**不重跑实现者已跑过的同层同套件**（同状态同层同套件多次运行 = 重复，V4）。全量重跑仅限：收口门禁（攒批最终证据）/ 契约面变更 / User 要求 / QA 判定影响面扩散（v0.6 触发条件）
- **V4 红/绿状态区分**：QA 证红与 Dev 证绿是不同状态，各跑一次不算重复；重复指同状态同层同套件多次运行。
- **V5 与 #45 分工**：本规则消「重复跑」（次数维度）；#45 优化单次成本（耗时/CPU），排期不受本规则影响。
- **实验方法铁律（v0.6 补，2026-08-02 QA 教训 #52）**：A/B 对照必须配对——同时刻交替 ≥3 轮取稳定值；单次/异时对照会被环境漂移污染（实证：假 key「12.4s vs >150s」为群聊高峰/网络异常伪差，真值 23-26s 无差）。结论入档前先审配对性。

## 7.5 并发协作（v1.0，2026-08-02 User 指示：Dev 干活时 Arch/QA 不应干等，工作流应支持并发）

**核心原则：等待只发生在真实依赖边——谁依赖谁的产出就等谁；不依赖的并行准备。串行阶段（评审/验收等 Dev 终态）是反模式，用「前置产物 + 阶段重叠 + 增量审计」消除。**

1. **前置产物先行（三线并行起点）**：
   - Dev 开工前，Arch 完成方案/契约评审（结构先定，实现不再等评审）；契约面（协议/持久化/schema）定稿即发 QA
   - 契约先行 → QA **红钉先行**：测试钉住契约，不等实现（红钉 = V0-① 自测证据，实现落盘后转绿锚定）
   - PM：范围/验收锚点在 Task Brief 先定，不拖到验收时
2. **实现期间（Dev 主跑，Arch/QA 并行准备自己的属主产出）**：
   - Arch：增量审计（依赖方向/契约面）——对 Dev **每步落盘 commit** 进行，不阻塞 Dev 后续步；发现接缝问题给「输入」而非「关卡」
   - QA：写测试钉（红钉先行）、预跑既有套件增量回归（对每步落盘态）、验收清单预写——全部在 test/ 属主域内
   - 交叉产出互不阻塞：Dev 不停步等 Arch/QA 中间结论；Arch/QA 中间结论作为 Dev 输入随时吸收
3. **阶段重叠（流水线）**：阶段 N 验收（QA 门禁）与阶段 N+1 方案设计（Dev/Arch）并行；阶段 N+1 红钉（QA）与阶段 N 收尾（Dev）并行
4. **门禁并发约束（防假并发）**：QA 宣布跑门禁时 Dev 不产出新改动（既有承诺保持）；在途产出先交 PM 落盘或明示 QA 延后；权威锚纪律不变（V0-② 只有落盘 commit 态可锚）；并发 = 各方在属主域内准备，不交叉抢改（src=Dev / test=QA / adr=Arch / 计划文档=PM）
5. **汇报节奏**：每步报告附「下一步可并行启动项」（如 Dev 报告下一步 X → Arch/QA 据此启动并行准备，不等完成通知）
6. **预跑窗口（v1.2，2026-08-02 教训：37d1b74 落盘后 integration 52 红）**：大拆解/装配重构类任务，PM 落盘前与 QA 协调预跑窗口——QA 对工作区 WIP 态预跑 integration（脏树预跑 = V0-① 参考证据，绿灯才落盘为权威锚 V0-②），防止中间态落盘为不可锚 commit；unit 绿不覆盖 WS 集成面，Dev 声明「unit 全绿」不等于 integration 可锚；落盘仅凭 unit 绿 = 违规风险
