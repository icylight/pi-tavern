# 头脑风暴状态收敛——「白板」模型（2026-08 采访定稿）

> 状态：**理解文档**（User 采访产出，尚未立项）
> 分支：`docs/brainstorm-convergence`
> 关联：问题源头 #105（README 位置议题 8+ 轮摇摆）；错误实践 #107（B 方案，实现 #110 已被 #111 revert）

## 1. 要解决的问题

头脑风暴/讨论轮次中，多个角色异步处理消息时**状态无法收敛**：

- 各角色基于自己看到的旧消息反复改变立场，对「当前状态是什么」产生冲突
- 多个不同 sequence 的裁决被不同角色同时引用为「当前」
- sequence/时间戳只解决消息先后，不回答「哪条当前有效」

## 2. 错误实践复盘：#107 建模错误

#107 的 B 方案把问题建模为「**裁决是状态**」，从而推导出机械化的产品方案：

- 决策存储（版本号、替代关系、最终结果）
- declare 命令 +「声明后才生效」的绑定生效点
- 环境文本注入「当前有效裁决」节
- 三层互补：机制 + 约定 + 提示词

**为什么错**：把「人随手记 + 共见」这个最简单的动作，建模成了「状态机 + 流程」。可靠性依赖流程纪律（declare、版本对齐），而纪律恰恰是最不可靠的一环；机制越重，维护成本越高，角色越不遵守。实现（#110）上线后被 revert（#111），实证走不通。

## 3. 正确模型：每人一块白板（采访定稿）

核心隐喻：**每个角色举在手里的一块白板**——不是机械的状态机，而是随时可写、举起来大家都能看见的板。

### 3.1 基本形态

| 维度 | 定稿 |
| --- | --- |
| 归属 | **每人一块自己的白板**（不是共享一块、不分「谁有笔」） |
| 内容 | **自由贴条**：想写什么写什么（立场、理解、分歧、疑问、待定）——不是「当前裁决」专用 |
| 时机 | **AI 自己决定**何时贴条、何时撕条（取下） |
| 可见性 | 白板**全群可见**，包括 User（主持人） |
| 通道 | **独立于消息流的部分**；但白板更新会发一条消息通知群聊 |
| 生命周期 | **跟随群聊**（讨论轮次），不跨群聊持久累积 |
| 限制 | 最大条数 + 单条最长字符，**可配置**；默认 **5 条 / 140 中文字符（280 英文字符）** |
| 朴素原则 | 「最开始就只是白板」——不做版本号、declare 仪式、替代关系、注入段分类 |

### 3.2 与 #107 的本质区别

| | #107（错误实践） | 白板（正确模型） |
| --- | --- | --- |
| 问题定位 | 哪条裁决当前有效（对历史做事实源裁决） | 每个人现在站在哪（当前立场互相可见） |
| 机制 | 状态机 + 流程（declare/版本/注入段） | 表达渠道（随手贴条 + 全群共见） |
| 更新语义 | 声明后才生效，需版本对齐 | 贴条即更新，撕条即撤销，天然只有「当前」 |
| 可靠性来源 | 流程纪律（不可靠） | 「所有人看同一块板」这个事实 |
| 收敛角色 | PM declare（归口职责升级） | User（主持人）看各人白板，口头收敛 |

### 3.3 解决什么

- 角色不用再从消息流归约别人的当前状态——扫一眼对方白板就知道
- 主持人有全局视图：各人白板一摆，分歧在哪、往哪收敛一目了然
- 白板的「最新覆盖旧」是天然语义，不需要版本号回答「哪条当前有效」
- 收敛动作仍是 User 拍板（权威不变），白板只是让收敛有依据、角色有共识锚点

## 4. 架构可行性骨架（Arch 反馈 2026-08，待 User 确认）

| 问题 | 方向建议 | 理由 |
| --- | --- | --- |
| 1 可见方式 | **通知 + 查询工具**（否决环境注入） | 注入与 #107 注入段同构已被证伪；快照必陈旧、全量注入上下文膨胀；复用现有「通知+增量拉取」原语，零新机制 |
| 2 通知内容 | **增量摘要**（仅变化的条），格式后置 | 仅提示=每次拉全量摩擦过大；带全量=刷屏+膨胀；配合现有防抖窗口 |
| 3 工具形态 | **独立新命令**（如 tavern_board set/remove），不进消息流 | speak=公开发言进消息流，白板=状态表达独立于消息流，通道必须分开；协议新增两个客户端消息 board_write + board_query（通知复用广播事件通道，不新增推送通道） |
| 4 持久化 | creator 侧群聊级独立文件 `boards/<groupId>.json`，随群聊**删除**即删（与 JSONL 同步）；关闭不删、供恢复读取 | 不写群聊 JSONL=不动现有格式（零漂移成本最低）；白板是临时表达渠道非档案；权威存储必须在 creator 侧（全群共见需要单一事实源） |
| 5 发言额度 | **不占额度** | 额度管公开发言、白板管状态表达，语义不同；5条/140字上限天然防滥用 |

### 耦合关系（Arch 提示）
- Q1 ↔ Q2 耦合：通知方案依赖增量摘要，方向一起定、细节后置
- Q3 ↔ Q5 耦合：占额度则 board_write 要带计数逻辑，方向一起定

### 影响面声明（契约变更三处，立项前四方确认 + ADR）
1. protocol 新增两个客户端消息：board_write（贴/撕/清）+ board_query（查全量）+ 一个服务器通知消息 **board_update**（独立消息类型，复用 broadcast() 广播通道，不混入 group_chat_update 的 events 批次——后者为 closed schema，混入=破坏性变更且误触发角色侧拉取；ADR-0007 §3 定稿）
2. 角色卡新增工具
3. 新持久化文件 boards/<groupId>.json

### 生命周期明确（Arch 补充②+⑤：关闭 ≠ 删除）
- **关闭**（creator 退出 /tavern-leave）：群聊 JSONL **保留**，board 文件同步保留——恢复（/tavern-resume）时按 groupChatId 读回白板，避免恢复后角色立场回到不可见、收敛链断裂
- **删除**（/tavern-resume 删历史，deleteGroupChatSession）：JSONL 进废纸篓/删除，board 文件**同步清理**（复用现有 trash/unlink 逻辑，trash 优先/unlink 回退/幂等）。**边界（best-effort，ADR-0007 §4 定案）**：会话删除是主动作——白板清理失败仅 warning 不阻塞，可能留孤儿文件（后续删除同类群聊不自动重试；孤儿不影响功能，仅占磁盘）
- 一句话：board 文件不独立决定去留，只跟群聊记录同生共死——记录在，白板在；记录删，白板删
- 群聊内跨轮次保留、不跨群聊累积

### 待定缺口：User 入口（Arch 补充③+④，双形态定稿，待 User 确认）
- **全量查看**：/tavern-status 增加「白板」小节（现有命令扩展，User 零新工具负担）
- **实时感知**：角色贴/撕条时 creator 终端实时显示「X 更新了白板」提示——与角色侧「喊一声」模型同构，User 不用主动刷
- 架构上为 creator 侧纯展示（board 数据本就在 creator 进程内存+文件里），**不新增协议消息，契约变更仍维持三处**
- 即：角色侧「喊一声+凑近看」，User 侧「喊一声+status 看全貌」，两边同构，闭环一致

### 待 User 确认的产品差异
「举在手里随时可见」在实现上是「被通知唤醒后主动查询」（白板挂墙上全群共见，变化时喊一声，想看清就凑近看），不是持续注入。
