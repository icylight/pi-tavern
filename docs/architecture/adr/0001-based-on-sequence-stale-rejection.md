# ADR-0001：发言前落后校验（based_on_sequence / stale 拒绝）

- 状态：**Accepted**（2026-08-01 冻结于 `docs/reference/websocket-protocol.md`，PR #30 实现并验收）
- 决策者：架构师（评审）、开发工程师（设计实现）、产品经理（需求定稿）、测试工程师（验收）
- 关联：GitHub ISSUE-013（#28），PR #30；扩展自 M7 增量拉取（`fetch_messages_since`）

## 背景

群聊中角色发言滞后于最新消息：一轮 9 分钟内 54 条公开消息中 43 条为「确认/无异议」类表态、43 条在等待裁决；Dev 曾基于滞后 3-4 条的消息发言。根因（User 采访定稿）：

1. **投递侧**：消息经 batch 累积、run 结束后投递积压而非最新（A 侧，ADR-0001 范围外，见 PR #30 实施）；
2. **发言侧**：角色发言前不确认最新消息，无任何校验（B 侧，本 ADR 范围）。

## 决策

### 1. speak 请求携带可选 `based_on_sequence`

`tavern_speak` 工具自动携带发送方最后已见公开消息序号（与增量拉取游标同一概念）。**缺省 = 不校验**：旧客户端/手动 WebSocket/既有测试不带该字段时行为与首版完全一致（平滑演进）；新客户端总是携带。

### 2. 服务端落后校验（B2）：业务拒绝，非协议错误

携带 `based_on_sequence` 时，若落后于服务端判定基准，请求被正常处理（`success: true`）但**不发布**，返回 `reason: "stale"` 与 `missing_sequences`（连续闭区间 `from..to`，纯提示信息）。

**落后判定排除自身（B6）**：比较基准是「最近一条**他人**消息的序号」（尾部向前扫描，跳过请求者自己的消息）——客户端拉取游标永不越过自己的回显（回显被客户端过滤），若按最新总序号比较，自己的消息会令下一次发言被误拒。

### 3. stale 语义：不发布、不消耗额度、不设置举手

区别于 `round_limit_reached`（额度耗尽 → 举手，表示「还有话说」）：stale 是消息过时，不是「还有话说」，故不设置举手、不消耗 Round 额度。

### 4. 补拉复用既有协议，不引入第二套拉取

speak 响应**不承担**拉取协议：`missing_sequences` 仅为提示，客户端被拒后不做立即拉取，只置 A2 既有「有更新」标记；当前 run 结束后由 A2 统一拉取覆盖（被拒时错过的消息与后续增量一并拉全）。同轮自动恢复上限 2 次（按响应 Round 快照变化重置），防消息洪峰死循环。

### 5. `latest_sequence` 为纯信息字段、非推进源

成功发布响应中的 `latest_sequence` 仅供信息展示；客户端不据此推进游标或任何已见序号（自身推进由 B6 排除自身判定保证），客户端不得依赖该字段做状态推进。

## 否决的替代方案

| 方案 | 否决理由 |
| --- | --- |
| 服务端计算「他人精确区间」供客户端逐条核对 | 复杂度高，speak 响应承担第二套拉取协议；补拉本有 `fetch_messages_since` |
| stale 与额度耗尽同语义（设置举手） | 语义混淆：额度耗尽 = 还想说但没额度；stale = 消息过时该补看，不是「还有话说」 |
| 被拒后客户端立即拉取注入 | 打断活跃 run，违背 M7「run 活跃只标记不投递」语义（A4/A5 保持） |
| 服务端按最新总序号比较 | 客户端回显永不越过游标 → 自己的消息导致下一次发言被误拒（B6 缺陷） |

## 影响面

- **协议**：`docs/reference/websocket-protocol.md` 已冻结（speak 请求/响应结构、stale 响应、`latest_sequence` 语义）。
- **实现**：`group-chat-input.ts`（投递路径 A 侧）、speak 校验（服务端）、quota 判定（被拒不计额度）。
- **兼容性**：`based_on_sequence` 缺省不校验，首版行为完全保留；响应 `reason` 字段首版枚举 `round_limit_reached` / `stale`。
- **验收**：PR #30 16/16 验收（B2 stale 拒绝全链路、B4 不占额度、B6 连发不误拒、legacy 缺省不校验）。

## 后续演进注意

- headless RPC 角色模式（ISSUE-014）下 `tavern_speak` 同样携带 `based_on_sequence`，校验路径与 TUI 角色一致，无分支。
- 若未来引入「他人精确区间」需求，应作为独立拉取协议演进，不在 speak 响应中扩展。
