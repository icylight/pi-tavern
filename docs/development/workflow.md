# PiTavern 工作流规范（Workflow）

> 目的：减少任务布置分歧、杜绝 main 直接改动，统一五方（PM/后端/客户端/QA/Arch）协作节奏。
> 属主：PM。变更须群聊声明影响面。
> 核心纪律：验证默认不跑（必须显式指定范围，不隐式跑全量/大面；全量仅限收口门禁/契约变更/User 要求）；git 写操作归 PM；push/merge 须 User 审批。

## 0.5 需求设计评审：第一性原理四问

任何需求/契约/新帧类型/新工具设计，**四问产出物缺失 = PM 不派工、验收口径不冻结**（关卡在派工前）。每问的输出物化（Arch 模板）：

1. **失败形态枚举了吗**——产出物：「失败形态清单」节。响应类型逐形态列（成功/每个拒绝态/错误码），speak 先例先抄后差异；docs-first schema 响应类型必须覆盖全部形态（anyOf 分支数 == 清单行数）。检查人：QA 契约核对轮逐形态核对。
2. **链路拆到底了吗**——产出物：「帧×消费路径矩阵」（websocket-protocol.md 附录）：行 = 帧类型，列 = codec 解码 | 实时注入 | 补拉 | 游标推进 | 未读 | 渲染 | TUI；每格填 ✓复用 / 差异化点 / 不适用（须写理由）。链路拆解须含接收者全链 + 旁观者全链 + 补拉路径 + 掉线竞态（每环写「谁消费、游标怎么动」）。检查人：Arch 评审逐格核对。
3. **相反视角过了吗**——产出物：验收规格「非主角视角」场景清单（旁观者/掉线/补拉/重入/并发 ≥3 类，每类一条行为断言）。检查人：PM 审验收口径时核对。
4. **假设不成立还成立吗**——产出物：意图词↔可证伪断言对照表。每条关键设计假设（不唤醒/不泄露/不占额度/不重复…）落一条行为断言；存在性断言不得替代行为断言；断言锚定真实消费链。检查人：QA 锚定层检查 + Arch 评审。

**锚定层检查（QA 验收规格固定小节）**：每条验收条目写「验证路径」（经 decodeServerMessage 解码断言 / 经 pullIncrement 消费断言 / 实时注入断言），禁「存在性/原始 JSON」表述。**消费链钉测命名规约**：端到端链路断言统一 `chain:` 前缀，验收报告含 `grep chain:` 审计行。**测试完成标准**：宣布完成 = `npm run check` 三段全过（biome + tsc + schema），vitest 绿 ≠ check 绿（tsc 门禁必须跑到）。**测试桩契约核对**：失败注入/错误模拟类测试，写桩前先读依赖实现或契约注释，stub 语义逐项对齐真实契约（容错/错误传播/返回值）——契约保证静默就模拟静默，契约保证抛错才模拟抛错；桩写完后经开发属主复评。

5. **复用语义核对表（新请求路径必过）**——产出物：新请求路径对照成熟路径核对表（文案分支/预算重置/错误码/举手透传/游标语义逐项核对）；共享语义优先抽共享 helper，差异化才放入口层；新入口的请求类型注册与响应校验必须核对齐全。检查人：Arch 评审 + 开发自审。

四问 + 核对表产出物随 Task Brief 回读确认一并核对；缺失项 PM 直接退回设计方，不进入派工。

## 0.6 e2e 测试剧本化与分层策略

**剧本化**：每个测试用例 = 一个剧本文件（test/acceptance/scripts/<scenario>.jsonc，注释即自文档化）；一个剧本 = 一个 it 用例；剧本 = 对话记录 + 期望断言（单一事实源），执行 = 解释器映射到既有驱动，解释器零业务逻辑 + 逃生舱代码钩子。**原子性三则**：自管 setup/teardown；零跨剧本依赖；单剧本可独立定向跑。

**分层策略（e2e 不硬上）**：e2e 必覆盖 = 真实链路高价值（投递多视角/重启恢复/多角色协作/验收锚定 1:1）。降层清单：时序/竞态 → integration 可控时序；拒绝形态全枚举 → unit 主 + integration 抽查；LLM 工具层 → unit mock；超时/恢复中间态 → integration 可控时钟；故障注入 → integration；性能/压力 → 专项基准不进 e2e。**降级流程**：QA 出降级报告 → Arch + 开发侧共同评审 → PM 收口随验收落盘；每场景有且仅有一层主锚；降层不降质。

## 0. 开工前必讨论（全员纪律）

除本地架构草稿起草/修订外，任何工作启动前先在群聊发布讨论（背景/方案/影响面/立场），**团队收敛 + PM 归口定案后才动手**——不得「看到评论/派发即开工」的边做边定。架构草稿讨论全部本地化（§5.5 纪律）。

评论响应分级：
- **缺陷修复**（事实清楚、口径单一）：认领即做 + 群聊播报；
- **设计/行为/契约变更**（新工具、语义变化、wire 面、持久化 schema）：先团队讨论收敛 + User 确认；
- 讨论期冻结相关实现。

## 1. 任务布置：Task Brief 五要素

**issue 写入时机**：需求提出后先**本地临时记录**（PM 私聊整理），团队讨论收敛 + **User 批准后**才创建 issue；**无 issue 不干活**。整体流程：**讨论收敛 → User 批准 → 开 issue → 分支开发 → 开 PR → User 合并**。关闭 issue 前置：QA 在 main 验证通过（树相等核对 + 引用 PR 门禁证据 + User 实测）+ User 确认。**验证环境**：User 负责将本机 pi 更新为最新 pi-tavern，QA 在更新后执行验证。

**User 原话最高权威**：PM 转译 Task Brief，但 User 原话始终是最高权威，PM 的摘要、推断或方案不得超驰原话。涉及歧义、删除/迁移、契约或范围变化时，PM 必须先原文引用 User 指令并附一句执行摘要，获得 User 明确确认后才动手；User 纠正理解则立即停止冲突方案回到原话重新确认。每项任务必须齐备：

1. **目标与范围**：做什么 + 明确不做什么
2. **落点约束**：分支名（PM 指定，跟随 issue）；main 默认不动
3. **验收锚点**：引用验收清单条目号；**无条目号的任务须先建条目再布置**
4. **验收口径冻结**：Task Brief 附「验收口径」段（验收方起草、PM 审、开工前冻结）——明确绿的定义；评审段引用同一口径；**中途改口径须 PM 裁决留痕**；验收规格强制含「锚定层检查」项（新 wire 帧/新工具/新消费面任务必须含真实链路端到端断言）
5. **执行人 / 评审人 / 验收人**
6. **依赖顺序**

## 2. 分支纪律（最高优先级）

- **main 是受保护基线**：任何角色不在 main 上直接提交/推送/改动（验证：`git rev-parse main origin/main`）
- **分支由 PM 控制**：一个 issue/批次一个分支，PM 指定分支名，User 确认；其他角色不自行开新分支
- **推送分支须 User 审批**：任何 `git push` 不得自主执行——先群聊声明推送内容与目标分支，User 审批后才可推送
- 所有改动落工作分支；角色卡、docs、scripts 同样遵守——**无例外**
- 分支合入 main 由 **User 亲自执行**；角色侧止于评审通过 + 证据齐备 + 宣布就绪
- **worktree 纪律**：默认单 worktree；例外使用须 PM 同意 + 群聊声明 + 记入 issue；收口随分支清理
- **扩展包更新操作纪律**：群聊运行期间禁止改写**运行中扩展的加载目录**（加载源 = agent clone，按 settings.json packages 的 git:...@commit 钉加载）。防线：① 包引用**永远钉 commit hash**；② 运行期禁止 pin 变更/`pi update`/`pi update --all`/clone reset 等一切会触发 clone 改写的动作；③ 切版本流程 = 停群聊 → 改钉 → 重启。例外：dev 仓库 git 操作不影响运行扩展。补充：显式 `-e` 覆盖会与钉版本双注册冲突，非推荐用法。
- **开 PR（PM 负责推送与创建/更新）**：PR 引用 issue 编号，附 Task Brief 五要素 + 验收证据；评审/验收在 PR 留痕；角色侧不执行 merge
- **CHANGELOG**：PM 归口维护；**更新粒度 = 发布批次**（收口时统一写入，日常 merge 不单独更新）；面向用户影响，不倾倒 git log
- **git 写操作统一归 PM**：add/commit、迁分支、stash、merge/rebase、push、PR/issue 操作一律 PM 执行，**不得委托**；git 只读（status/log/diff/fetch）保留用于排查
- **PM 落盘职责边界**：PM 对非属主文件仅执行 git 归口；机械修复可代做但须先群聊声明并请属主复核；语义修改一律归属主
- 动手前先 `git status` + `git branch --show-current`

## 3. 沟通与确认闭环

- **私聊-批准-同步**：需求澄清/方案讨论 → PM 与 User 私聊；User 批准才同步群聊。群聊 = 协作与定稿同步现场；issue 评论区 = 可靠结论载体
- **私聊同步义务**：User 与任一角色私聊的决策/指示/新事实**默认不自动进入群聊**；达成共识后主动同步群聊交 PM 归口，不留私聊盲区；未达共识的中间讨论不转达（过早同步视为无效）
- **Issue 同步策略**：User 新 issue 不一定在群里同步；未明确时 PM 自行判断，**倾向不同步**；影响优先级/需成员行动/阻断当前/触碰契约面 → 同步（一句话 + 链接）
- **User 消息响应规则**：唯一默认响应者 = PM；PM 点名或议题明确属主时对应角色才答。**事实增量原则**：同议题一方已答，他方只补新事实；纯附和/复读不发。交叉消息免补发；跨通道不复述；角色间讨论不受限（架构草稿本地化纪律除外）
- **三句确认闭环**：① 布置确认——User 指示 → PM 一句话回读「做 X，落分支 Y，不动 main，完成后 Z 算达标」→ User 点头才开工；② 执行确认——执行人收到 Task Brief → 一句话复述理解 → 无歧义再动手，有歧义当场问；③ 完成确认——完成汇报附证据 → 验收人按条目号验收 → 宣布就绪
- **白板协作（tavern_board）**：待裁决/待审批/里程碑状态 = PM 板；评审立场 = 各角色板；贴前 query 查重；上限 5 条/140 字；裁决/完成即撕或更新为结论

## 4. 信息流与对齐

**拓扑**：PM → Arch/QA → 后端/客户端（两阶段并行）。阶段一：PM 派发需求 → Arch 出架构设计 ∥ QA 出文档级测试用例；阶段二：Arch 写 UT ∥ QA 写红测（集成/验收）；Arch ↔ QA 互评；任一方测试完成 → 后端/客户端开工。**单元/集成测试属主 = Arch；acceptance 属主 = QA**。

**三次握手**（固定 3 条消息）：SYN 提出分歧 → SYN-ACK 响应理解+己方立场 → ACK 确认一致。有分歧就握手，无快速通道。

**交付链**：后端/客户端交付对象 = **只有 Arch**；Arch 验收通过后再交付 QA 与 PM；QA = 跑测试；PM = 逐行 code review（源码与测试均在范围）；交付链串行，团队链上留痕归口 PM 发布。

**交付对抗协议**：PM/QA = 业务一方，Arch/后端/客户端 = 技术一方；对抗是常态分工。**总则：交付 = 进入对抗流程而非宣告——默认不通过，证明才放行**：
1. **交付方自对抗**：宣布完成必附自查证据 + **已知弱点声明**（3 个最可能被挑战的点）
2. **交付门槛检查**：残留扫描类检查强制进交付门槛（tsc 清零 ≠ 正确，wire 形状靠 codec/集成钉测与残留扫描）
3. **Arch 评审 devil's advocate**：先假设有错再找证伪证据；阻断级意见 = 打回重做（无「有条件通过」）；B 级 = 执行方当场表态；评审结论附可证伪路径
4. **QA 验收对抗场景**：验收必含 ≥1 个对抗性构造；QA 交证据前 Arch 核证据本身
5. **PM 逐行 review**：存疑点不因验收通过而跳过
6. **对抗检查清单**：按 `docs/development/review-checklist.md` 逐项攻击；新检查项只补可执行规则
7. **反驳权**：评审意见后 1 个 commit 周期内可反驳，反证据须具体；过期视为接受

**四次挥手**（固定 4 条消息）：FIN 完成声明+证据 → ACK 收到 → FIN 验收结论 → ACK 确认关闭。仅可验收节点走挥手。

**分歧裁决线**：文档/需求分歧 → PM 裁决；技术/契约分歧 → Arch 裁决；Arch 架构产出以文档形式提交 PM 裁决；裁决记录存本地不直接写 GitHub。

## 5. 分歧仲裁

| 争议类型 | 仲裁者 | 依据 |
| --- | --- | --- |
| 范围之争 | PM | `docs/development/acceptance.md` 与对应 GitHub Issue |
| 契约之争 | Arch | `docs/reference/` 契约文档 + `docs/architecture/` 现行设计 |
| 质量之争 | QA | 可复现证据（最小步骤 + 期望/实际差异） |
| 执行落点之争 | User | User 优先（默认分支、main 不动） |

## 5.5 第一性原理规则（思维方法，全员适用）

**定义**：任何决策先回到「不依赖假设就为真」的根本事实再向上推理；禁止以「类比/惯例/大家这么做」作为决策理由（类比只作假设来源）。

**触发**：决策不可逆/影响面大、存在分歧、模糊新领域、复杂问题。不触发：日常低风险可逆有默认值的事直接走（防滥用）。

**操作四步**：① 识别问题（定义真问题，非表面症状）；② 分解到基本单元（系统不变式/协议契约/已证实事实，追问「还能再拆吗」）；③ 质疑假设（标注事实/惯例/猜测，惯例与猜测必须给可证伪判据）；④ 重建与验证（方案附「若哪条假设不成立则失效」脆弱点声明）。

**反模式（禁止）**：类比决策（类比只作假设来源）；假设当事实；惯例辩护（经受「当初的假设现在是否仍为真」检验）；结论先行（先结论后论据一律退回重述）。

**自查四问**：我怎么知道这是真的？断言拆到最底层了吗？相反的证据或视角是什么？假设不成立方案还成立吗？

**角色映射**：PM——需求分析先问本质，范围裁决拒绝「别人都这么干」；Arch——从系统不变式/协议契约评审，**架构草稿本地化纪律**：讨论全程（草稿、中间结论、往返、对抗）只在本地整理，不入库、不在群聊展开；定稿后把精简结论（最终决策/必要理由/影响/替代关系）直接并入对应现行文档，仓库不设草稿目录；群聊只同步一行定稿结论；需 User 拍板只一次呈现；涉及验收锚语义附一行「影响锚点：<条目> 不变 / 需同步」；文档终审默认 1 轮，User 要求时复查 1 轮；后端/客户端——实现前问「该行为的最简正确形态是什么」，调试用 5 Whys 追根因；QA——断言有效性质疑（测试通过≠测到目标，红基线必跑）。

**关系**：本规则是思维底座（§8 症状≠根因、契约零漂移、验收驱动、交付对抗均是其实例）；冲突时本规则优先。

## 6. 默认值

- 引用 GitHub issue 带 updated_at 时间戳；质疑「已改/未改」先报自己读的版本；以 GitHub API 直读值为权威
- **接力棒发言协议（单棒制）**：① 版本锚前置（引用先报读取版本，无锚引用无效）；② 任一时刻仅持棒者发言，末尾显式递棒，非持棒者不说话；③ User 可随时接棒/插话（最高优先）；④ 工作线可并行但发言权单棒；⑤ §7.7 异常发现即报不受棒制限制，报完即静默；⑥ 已定案不重议（再议需新论据）；⑦ 一轮一议题
- 默认落点：PM 指定分支；main 不动；默认只读（讨论阶段不写文件/issue）；默认范围：User 没提的不做；默认提交：一个逻辑一个 commit，属主文件改动到工作区（不自行 git add/commit），PM 统一检查落盘；禁 `git add -A`

## 7. 任务状态流转与验证

**流转**：讨论收敛 → User 批准 → 开 issue → 布置 → 回读确认 → 分支开发 → 开 PR → 评审/验收 → User 合并 → QA 在 main 验证（树相等核对 + 引用 PR 门禁证据，不重跑全量）→ 关闭 issue。

**协议变更（docs-first）**：消息格式唯一手写处 = src/protocol/schema/*.jsonc；改定义文件 → `npm run docs:types` 重新生成 → 提交定义 + 产物（禁手改 generated/）；`npm run check` 尾部只读 --check，忘生成被拦截。

**状态汇报归 PM**：PM 向 User 汇报；其他角色与 PM 对接，不直接向 User 汇报。

### 验证留痕与分级验证

**核心原则：同一状态（同 hash + 同层 + 同套件）只验证一次；留痕即证据，引用不重跑。**

**验证分类**：验证锚（红→绿闭环/验收门禁）保留独立双证；常规状态确认（lint:layers/基线绿/grep 残留）引用留痕不重跑。

**默认不跑**：验证动作必须显式声明「跑什么」（命令含目标文件/套件/定向）；全量触发仅：① 收口门禁 ② 契约变更（影响面=全链）③ User 要求 ④ QA 判定（影响面扩散超出定向能力）。

**V0 证据格式与四级锚定**：留痕一行「命令 | 结果摘要 | hash@层 | 环境」（层 = unit/integration/acceptance/全量；环境两类锚不可混用——① 验收门禁锚 = references/pi@子模块 commit + node 版本；② 真实环境锚 = 全局 pi + node）。acceptance 证据必须含门禁锚；跨类引用 = 环境漂移 → 重跑受影响层；未留痕视为未发生。锚定四级：① 自测/红测（含未提交改动）：标注「含未提交改动，基线 HEAD=<hash>」，仅参考/测试有效性证明，不作权威证据；② 权威锚 = PR 门禁分支头（committed tree），唯一可引用锚，跑启动时记 HEAD；③ 同树引用：已提交树绿跑可直接引用；④ 变更重跑触发：分支新提交/环境漂移 → 重跑受影响层。脏工作区陷阱：HEAD 不含被测内容时禁止裸引用 hash。

**V1 分级验证阶梯**：红测链（QA）只跑新增/受影响文件证红，留痕失败阶段；后端/客户端自测：unit 受影响层 + 红测转绿目标 + integration 可跑（秒级）；证绿反向引用红测（「对应红测 <hash> 阶段 X 已修复」），红绿两行互相锚定；**后端/客户端不跑 acceptance 全量**。评审（Arch/QA）：diff 审查 + 只跑被改动文件 unit 抽查；**Arch 承担代码评审**（正确性/边界/错误处理/命名/测试充分性），评审风格从严（死代码/重复/命名/未简化一律指出，区分阻断/B 级，「干净」是合入前提）。

**默认门禁 = 分层压缩**：unit 全量 + integration 全量（秒级不裁）+ acceptance 只跑受影响文件（定向）。全量按需触发（V1 四条件）。执行细节：跑前 `git status` + `git rev-parse HEAD` 确认分支头且工作区干净（脏树不跑门禁）；定向跑留痕附受影响文件清单 + HEAD^{tree}；QA 宣布跑门禁时后端/客户端不产出新改动。

**V2 双因子重跑判定**：重跑 = ① 涉及文件变更（src/test/docs）→ 重跑受影响层；或 ② 影响面声明（实现者随证据带「影响面」字段：受影响层小枚举 + 一句理由）。QA 判定 = 声明 + 只读 diff 交叉核对（重点扫异步/定时/超时/轮询类改动）；无触发 → 引用旧证据。

**V3 证据复用与树相等**：同 hash 直接引用；main 验证 = `git rev-parse main^{tree} == PR头^{tree}` + 引用 PR 门禁证据 + User 实测，不重跑全量；树不等才重跑受影响层；树相等只证内容不证环境——对照证据行环境上下文（pi 版本号），漂移则重跑。**逐 PR 验收**：树相等核对 + 引用实现者证据 + 仅新增/受影响用例定向抽查；不重跑同层同套件。

**V4 红/绿状态区分**：QA 证红与后端/客户端证绿是不同状态，各跑一次不算重复。

**实验方法铁律**：A/B 对照必须配对（同时刻交替 ≥3 轮取稳定值）；单次/异时对照会被环境漂移污染；结论入档前先审配对性。

**红绿双向锚定模板**：证红 = 命令 | 红@失败阶段 | hash@层（参考级）；证绿 = 命令 | 绿，对应红测 <hash> 阶段 X 已修复（修复点）| hash@层。

## 7.5 并发协作

**核心原则：等待只发生在真实依赖边；不依赖的并行准备。串行阶段是反模式，用「前置产物 + 阶段重叠 + 增量审计」消除。**

1. **前置产物先行**：开工前 Arch 完成方案/契约评审（结构先定）；契约面定稿即发 QA → QA 红钉先行；PM 范围/验收锚点先定
2. **实现期间**：Arch 增量审计（对每步落盘 commit，发现接缝问题给「输入」而非「关卡」）；QA 写测试钉/预跑增量回归/预写验收清单；交叉产出互不阻塞
3. **阶段重叠**：阶段 N 验收与 N+1 方案设计并行
4. **门禁并发约束**：QA 宣布跑门禁时后端/客户端不产出新改动；在途产出先交 PM 落盘或明示延后；并发 = 各方在属主域内准备（src=后端/客户端 / test=QA / 架构文档=Arch / 计划文档=PM）
5. **汇报节奏**：每步报告附「下一步可并行启动项」
6. **预跑窗口**：大拆解/装配重构类任务，PM 落盘前 QA 对工作区 WIP 态预跑 integration（脏树预跑 = 参考证据，绿灯才落盘为权威锚）；unit 绿不覆盖 WS 集成面
6.5 **落盘文件清单核对**：PM 落盘前 `git status` 文件集与声明范围逐项比对，清单外一律不落；禁 `git add -A` 盲落
7. **acceptance 孤儿进程清理**：global-setup 自动 killOrphanedPiProcesses（pkill 仅匹配本仓 references/pi/pi-test.sh 路径）

## 7.6 协作机制（PM 是总收尾者）

**总则：PM 主动收敛、关闭、推动，不让事项悬挂；各角色配合收尾。**

1. **状态真相唯一化**：状态以 git log/工作区为准；动手前自查三连（branch + status + log -3）；PM 落盘后发 commit 索引；同一事实只发一次
2. **分工矩阵**：钉测类 = QA 主 + Arch 主 unit 层；实现/基建类 = 后端/客户端；文档/纪律类 = PM 主 + 属主出内容；评审/调研类 = Arch；每 issue 一条关键路径 + 其余角色并行预研
3. **等待窗口显式化**：等待真实依赖期间声明可并行项
4. **钉测即验收模式**：修复类 issue 默认拆为可钉测断言（钉测 ↔ 修复一一对应）；不可钉测面（TUI 视觉/真实 LLM）才走人工验收
5. **PM 收尾动作**：落盘攒批（约 15 分钟粒度 + commit 索引）；验收条目由验收方起草 PM 审；风暴收敛后立即给默认执行方案
6. **验收两级制**：自验（红绿 + 留痕）+ QA 终验——「关键面清单」（契约面/门禁面/持久化面必全验）内全验，抽验仅限低风险常规批次
6.5 **风暴自动收敛**：15 分钟无实质增量 → PM 整理收敛稿交 User（收敛仍归 User，PM 不代拍板）
7. **前馈闭环**：里程碑验收时 Arch 回注「预估 vs 实际」偏差，形成闭环校正
8. **双环回顾**：里程碑收口附 5 分钟流程回顾，产出进架构优化待办清单
9. **测试分层下沉**：仅「进程内可等价验证」场景可 acceptance → integration；真实 pi e2e 不牺牲
10. **双 worktree（声明制）**：并发任务经声明可双开；验收/门禁错峰（run-tests 端口/临时目录/pkill 作用域共享）
11. **红线不动**：git 写操作归 PM、验证默认不跑、契约零漂移、push/merge/PR 归 PM——推送审批保留逐次

## 7.7 异常报告流程

**总则：发现即报，禁止「查清再报」**——先报现象 + 影响，排查过程边做边报。

1. **触发（必报）**：非预期测试红（钉测红 = 预期不报）；环境异常；计划偏差（基点错/方案偏离/范围变化/属主越界）；卡点；实验异常
2. **报告格式**：现象 + 影响 + 已确认事实（证据/日志/命令）+ 求助项；必要时附最小复现
3. **闭环**：报群 → 认领 → 定案（修复/降级/挂起）→ 结果回报；无人认领 PM 兜底
4. **例外**：无
5. **与 §8 关系**：本流程是上游（发现即报），§8 是下游（根因深挖）

6. **测试失败即时报告**：每次跑完即报（命令 | 结果摘要 | 失败点 | 下一步）；挂起/环境异常发现即报；定位分段播报（≤15 分钟一报）；收口门禁每层一报。**输出落盘防截断**：重定向落盘（`2>&1 | tee /tmp/run.log`），失败从完整日志提取「Failed Tests」段。**bug 报告业务场景化**：「谁、在什么场景、会怎样」（业务语言），技术细节作证据附后
7. **发现问题 ≠ 定位问题**：QA 职责止于发现与报告，不独自闷头定位；定位由相关域开发角色认领，所有相关方共享定位过程

## 7.8 架构优化点内嵌机制

**总则：小粒度架构优化点走「登记 → 设计方案内嵌」通道，不单独开 issue。**

1. **登记**：Arch（及各方）发现的小粒度优化点（非契约变更、非独立交付物、不达 issue 规模）→ 登记 `docs/development/architecture-backlog.md`（Arch 属主，只保留优化点/建议方案/状态）——发现即登，随所在分支/PR 同批合入
2. **内嵌**：Arch 每次设计/评审方案时**必须扫描待办清单**，相关优化点并入方案设计；不采纳的显式记录理由
3. **边界**：契约变更、独立交付物、跨里程碑规划仍走正常 issue 流程
4. **勾销**：优化点落地后 Arch 在清单勾销（注明随哪个 commit/里程碑）
5. **验收锚**：设计方案输出附「待办清单核对」段
6. **顺手优化扫描**：Arch 每次批次归口时主动扫描，按「同文件/同域碰触 + 零行为变化 + 低风险」筛选候选交 PM 归口；收口前复核，不留静默区

## 8. Bug 排查流程

**核心原则**：① 复现先行（反馈回路是唯一关键技能）；② 症状 ≠ 根因（改症状不是修复）；③ 相关 ≠ 因果（宣布根因前须受控复现或 ≥2 条独立实证链）；④ 5 Whys（直到落在可行动的流程缺口）；⑤ 证据可复核（附「另一个工程师能复核的证据」）；⑥ 留痕闭环（无论结论如何都写 report）；⑦ 修复钉测（回归测试先红后绿）。

**S0 症状卡（PM 采访 User）**：5W1H 模板，缺项标注「待补」不阻塞开查——操作时间线/现象/时刻与频率/影响面/恢复动作/会话与终端/日志与报错/期望行为。

**S1 环境快照**：加载源（settings.json 钉 + clone HEAD）；进程清单（pid/启动时刻/加载路径）；版本矩阵（运行时 pi/测试锚定 pi/扩展 HEAD——三者不一致 = 门禁级关注项）；仓库路径声明（dev 仓库 vs 扩展 clone）；会话文件用身份锚确认属主；快照附时间戳入 issue 作证据基线。

**S2 复现评估（QA 主导）**：可复现 → QA 红绿测试先行；不可复现 → 观测增强 + 假设分层，升级观察项；评估入 issue。

**S3 假设循环**：每假设标置信等级（实证/相关未复现/推测）+ 可证伪判据，主动证伪；「根因」一词保留给「已受控复现或 ≥2 条独立实证链」，否则称「候选根因」。

**S4 根因门禁（PM 把关）**：宣布根因须受控复现或 ≥2 条独立实证链；否则标注「机制实证 + 相关吻合，未受控复现」；复现不了 → 按「操作风险/观测项」降级。**定案记录与显式作废**：定案 = 结论 + 时刻 + 责任人 + 证据链 seq 号（入 issue）；翻转须群聊显式作废旧结论（引旧 seq），新旧不并存。**结论-产出绑定清单**：每根因定案登记关联测试/修复文件，收口逐项核对。

**S5 修复 + 验证**：因果修复；回归测试先红后绿；版本缺口补跑；**合入前 check 清零**（无 CI，check 为本地人工门禁——每批合入 main 前 `npm run check` 全绿留痕，与定向绿、V0 留痕构成合入三件套；biome/TS 版本变更 → 全量 check 清零）；**git hook 自动化提醒**（husky pre-push 跑 `npm run check`，非零拒绝推送——本质 = 纪律提醒，`--no-verify` 可绕过，不替代纪律）；**测试有效性检查**（写钉测后强制失败演示 + 红基线必跑；防 schema 静默丢弃/mock 未接通陷阱）。

**S6 复盘收口**：5 Whys 复盘流程断点 → 改进项落本文档；issue 关闭前置：User 实测确认 + 根因置信等级留档。
