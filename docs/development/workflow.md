# PiTavern 工作流规范（Workflow）

> 目的：减少任务布置分歧、杜绝 main 直接改动，统一五方（PM/后端/客户端/QA/Arch）协作节奏。
> 属主：PM。变更须群聊声明影响面。
> 版本：v1.3（默认不跑用例：——不隐式跑全量/大面，验证必须显式指定范围，只跑改动涉及的；全量仅限收口门禁/契约变更/User 要求；v1.2 内容不变）

## 0. 开工前必讨论（2026-08-08 苍蓝星定：全员纪律）

任何工作（实现/钉测/文档/评审调整）启动前先在群聊发布讨论（背景/方案/影响面/立场），**团队收敛 + PM 归口定案后才动手**——不得出现「看到评论/派发即开工」的边做边定（#144 P1-4 教训：新工具 + 游标语义属设计类变更，走了快速路径）。

评论响应分级：
- **缺陷修复**（bug 事实清楚、口径单一，如 wire 安全校验、文档同步、回退链截断）：认领即做 + 群聊播报；
- **设计/行为/契约变更**（新工具、语义变化、wire 面、持久化 schema）：先团队讨论收敛 + User 确认，才执行；
- 讨论期冻结相关实现（已交付部分保留，待定案调整）。

## 1. 任务布置：Task Brief 五要素

**issue 写入时机**：讨论好了才写 GitHub issue——需求提出后先**本地临时记录**（PM 私聊整理，不写 GitHub、不动仓库），团队讨论收敛 + **User 批准后**才创建 issue，然后进入布置/执行流程；**无 issue 不干活**（issue 是开工令）。整体流程：**讨论收敛 → User 批准 → 开 issue → 分支开发 → 开 PR → User 合并**。issue 状态与任务状态同步流转（见第 6 节），**关闭 issue 前置条件：QA 在 main 验证通过（树相等核对 + 引用 PR 门禁证据 + User 实测）+ User 确认**。**验证环境：User 负责将本机 pi 更新为最新 pi-tavern**（真实环境验证），QA 在更新后的环境执行验证（按 §7 验证阶梯，不重跑全链）。

User 自然表达指示 → **PM 负责转译成 Task Brief 并回读确认**（User 不填模板）。每项任务必须齐备：

1. **目标与范围**：做什么 + 明确不做什么（边界，如"其他不动"）
2. **落点约束**：分支名（**PM 指定，跟随要开发的 issue**）；main 默认不动，例外须 User 明示
3. **验收锚点**：引用验收清单条目号（如 A1-A6 / U1-U4）；**无条目号的任务须先建条目再布置**（防口径漂移）
4. **验收口径冻结（控制论优化，2026-08-06 苍蓝星点头）**：Task Brief 附「验收口径」段（验收方起草、PM 审、开工前冻结）——明确绿的定义（哪些用例/哪些层/哪些已知中间态）；评审段引用同一口径；**中途改口径须 PM 裁决留痕**（M1 绿口径 A/B 讨论教训）
5. **执行人 / 评审人 / 验收人**：谁主做、谁评审、谁验收
6. **依赖顺序**：前置条件与后置动作

## 2. 分支纪律（最高优先级）

- **main 是受保护基线**：任何角色一律不在 main 上直接提交、推送、改动；main 保持与 origin/main 一致（验证：`git rev-parse main origin/main`）
- **分支由 PM 控制**：分支分配跟随要开发的 issue——一个 issue/批次一个分支，PM 在 Task Brief 中指定分支名，User 确认；其他角色不自行开新分支，分支归属争议由 PM 裁决
- **推送分支须 User 审批**：任何 `git push`（含工作分支推送、PR 分支）一律不得自主执行——先在群聊声明推送内容与目标分支，User 审批通过后才可推送；未审批的推送视为违规
- 所有改动落工作分支（`feat/*`、`fix/*`）；角色卡、docs、scripts 等一切文件改动同样遵守——**无例外**
- 分支从 main 切出（`git checkout -b feat/xxx main`），逻辑独立、一个任务一条分支（或按 User 决定并入既有分支）
- 分支合入 main 由 **User 亲自执行**（指示），角色侧止于评审通过 + 证据齐备 + 宣布就绪
- **worktree 纪律（v0.5 补充**：默认单 worktree——评审/开发一律在主仓库分支内做，不建额外 worktree；worktree 仅例外使用（并发任务需隔离运行时），创建前须 PM 同意 + 群聊声明（属主/任务/目录）+ 记入 issue，未声明的 worktree 一律视为违规（#49 后清理时逐层确认的根因即两个 worktree 从未声明）；生命周期：任务收口随分支清理一并移除，不留未声明旁支
- **扩展包更新操作纪律（实证；独立操作风险，非 #83 根因——#83 根因 = #77 状态广播自激循环，见 §8 与本批修复）**：群聊运行期间禁止改写**运行中扩展的加载目录**（加载源 = agent clone `~/.pi/agent/git/github.com/icylight/pi-tavern`，按 `~/.pi/agent/settings.json` packages 的 git:...@commit 钉加载）。机制（QA 实证修正）：pi 包管理器对**未钉 commit 的 git 包引用**执行 ensureGitRef（fetch + reset --hard + clean + 必要时 npm install）——14:52:36 sync（触发者未确认）与 15:31:21 sync（User 15:31:15 `pi update --all` 手动触发，zsh 实证）与掉线时刻相关吻合，但**因果未证实**（受控实验 v1/v2：单进程场景 src 改写 + 完整三连副作用均未复现掉线；真实场景差异 = 多进程并发）；**钉 hash 后 ensureGitRef 幂等（localHead==target → 零改动）** = 回滚后稳定的机制根因（QA 实证）。直接子机制未完全实证：src 改写本身 30s 观察不掉线（QA 复现实验），候选 = update 完整副作用（npm install 重写 node_modules / clean 删文件 / 与运行中扩展竞态），四步对照复现（reset/clean/npm install/全三连）排期中。防线二：① 包引用**永远钉 commit hash**（唯一防改写手段；worktree 隔离不了 clone 目录）② 运行期禁止 pin 变更/`pi update`/`pi update --all`/clone reset 等一切会触发 clone 改写（含后续 sync）的动作——注意 pin 变更本身不掉线，掉线发生在「pin 变更/更新命令 + 新 pi 进程启动触发 sync 改写 clone」的组合；③ 切版本流程 = 停群聊 → 改钉 → 重启；可选保险丝（文档化）：同步前先确认群聊未在运行（active descriptor 存在则先停）。**例外**：dev 仓库（/home/wangsen/code/pi-tavern）的 git 操作（分支/commit/pull/merge）不影响运行扩展（加载源 = clone，pi 源码 `getGitInstallRoot` 实证 + fix/issue-83 开发期间群聊全程稳定），不受此限。**补充**：扩展加载唯一入口 = settings.json 钉（clone 目录）；显式 `-e` 覆盖会与钉版本双注册冲突（tavern_speak 工具冲突实证），非推荐用法。
- **开发完成开 PR（PM 负责推送与 PR 创建/更新**：PR 标题/描述引用 issue 编号，附 Task Brief 五要素 + 验收证据（命令 + 结果）；评审（Arch）与验收（QA）在 PR 上留痕；角色侧一律不执行 merge，PR 就绪后宣布，由 User 合并
- **变更记录（CHANGELOG**：`CHANGELOG.md` 由 PM 归口维护（生成 + 更新，其他角色不提改）。**更新粒度 = 发布批次**（2026-08-08 苍蓝星拍板：每次 merge 单独写太频繁）——0.3.0 等发布收口时统一写入该版本全部条目，日常功能 merge 不单独更新、不为 CHANGELOG 单独开 PR；条目面向用户影响，不倾倒 git log（Keep a Changelog 格式 + 语义化版本）；PR 描述如需 changelog 条目，由 PM 在 Task Brief 中说明
- **git 写操作统一归 PM**：git add/commit、迁分支、分支创建/切换/删除、stash/apply、merge/rebase、push、PR 创建/更新/评论、issue 操作一律由 PM 统一执行，**不得委托**。任何角色不得以「拆分自己的工作区改动」「恢复现场」等理由自行执行 git 写操作——需要拆分支/暂存时，先声明工作区内容归属（「工作区 = X 改动集」），由 PM 执行拆分；commit 内容属主=各角色；git 只读（status/log/diff/fetch）保留用于排查
- **PM 落盘职责边界（User 观察 + Arch 审计）**：PM 对非属主文件仅执行 git 归口操作（add/commit/分支）；机械修复（格式/TS 语法级）可代做但**须先群聊声明**并请内容属主复核；语义修改一律归内容属主——PM 反馈问题 → 属主改 → PM 落盘，PM 不直接代改（#90 W1-c 教训）
- 动手前先 `git status` + `git branch --show-current`：确认所在分支正确、工作区无他人未提交改动

## 3. 沟通与确认闭环

### 私聊-批准-同步
- 需求澄清、方案讨论类 → **PM 与 User 私聊**；收敛成结论后，**User 批准才同步群聊**
- 群聊 = 讨论现场（User 可看）；issue 评论区 = 可靠结论载体；两者承载不同职责

### 私聊同步义务（私聊倾向不同步，所有人都要遵守）
- **事实前提**：User 与任一角色的私聊内容（决策倾向/指示/新事实/意见）**默认不会自动进入群聊**，其他角色不可见
- **同步义务**：任何角色与 User 私聊，凡涉及决策倾向/指示/新事实，**达成共识后**主动同步到群聊（内容摘要 + 状态标注），交 PM 归口记录，不留私聊盲区
- **同步时机（User 澄清：同步太早了）**：私聊是讨论区，**未达共识的中间讨论不转达**；过早同步会误导群聊——达成共识后才同步；未同步视为未发生，**过早同步同样视为无效（以共识版为准）**

### Issue 同步策略
- User 新提出的 issue **不一定要在群里同步**；
- User 明确要求同步 / 不同步时，按指示执行；未明确时由 PM 按场景与相关度自行判断，**倾向不同步**；
- 判断参考：纯登记（无排期、不涉及他方动作、不影响当前序列、无契约面变更）→ 不同步，细节留在 issue；影响优先级、需成员行动、阻断当前工作、触碰契约面 → 同步（一句话说明 + issue 链接）；
- 同步形式从简：结论与细节放 issue 评论区，群聊只发摘要。

### User 消息响应规则（v0.5，群里聊天全员回应有点乱）

- **唯一默认响应者 = PM**：User 群聊发言 → 仅 PM 回应（回读/确认/提问/汇报）；PM 点名或议题明确属主时对应角色才答
- **事实增量原则**：同议题一方已答，他方只补新事实（新核验/纠错/新承诺）；纯附和/复读/重复确认一律不发——§7「同一状态只验证一次」在对话层的延伸（同一消息只应答一次）
- **交叉消息免补发**：消息交叉导致的重复状态以最新文件/分支状态为准，不再补发对齐（本轮多次交叉补发全属此类）
- **角色间讨论不受限**：非 User 消息的团队协作维持现状
- 汇报口径不变：PM 为唯一对 User 汇报点

### 三句确认闭环（防错位核心）

1. **布置确认**：User 指示 → PM 一句话回读「做 X，落分支 Y，不动 main，完成后 Z 算达标」→ User 点头才开工
2. **执行确认**：执行人（后端/客户端/QA）收到 Task Brief → 一句话复述理解 → 无歧义再动手；有歧义当场问，不猜测（ISSUE-003 教训）
3. **完成确认**：完成汇报附证据（命令 + 结果）→ 验收人按条目号验收 → 宣布就绪

### 白板协作机制（tavern_board，v1.6，2026-08-08 苍蓝星指示启用：裁决点防被消息流淹没）

- **归口分工**：待裁决点/待审批点/里程碑状态 = PM 板（裁决台账：裁决后更新为结论，可追溯）；评审立场/影响面 = 各角色板；证据留痕仍在群聊/issue
- **进度上板**：各角色把己方进度、交付状态、待办贴自己板，进度推进即更新撕换；消息流只发结论与证据引用，不重复贴板内容
- **纪律**：贴前 `tavern_board query` 查重（同一条归 PM 板不重复贴）；上限 5 条/140 字，超限先撕旧再贴新；裁决/完成即撕或更新为结论

## 4. 信息流与对齐（v0.3）

### 信息流拓扑：PM → Arch/QA → 后端/客户端（两阶段并行）

```text
阶段一：PM 派发需求 → Arch 出架构设计（文档形式）∥ QA 出文档级测试用例
PM 评审（并行不阻塞：Arch/QA 不等评审结果直接进阶段二）
阶段二：Arch 写 UT（单元测试）∥ QA 写红测（集成/验收测试）
Arch ↔ QA 互评（需求对齐；不是后端/客户端开工条件）
触发：任一方测试完成 → 后端/客户端开工
开工后：后端/客户端以 PM 需求为准，自主思考实现；与 Arch/QA 有分歧 → 继续对齐交互
```

- **单元测试属主 = Arch**（单元测试可以让架构师写）
- **集成测试属主 = Arch**（集成测试让 Arch 写，不再让 QA 写）；**acceptance 属主 = QA**（不变）
- 对齐目的：前期三次对齐（PM↔Arch、PM↔QA、Arch↔QA）让后端/客户端拿到的输入收敛

### 对齐交互：三次握手（固定 3 条消息，无快速通道）

```text
SYN 发起方 → 对方：提出分歧/新信息
SYN-ACK 对方 → 发起方：响应理解 + 己方立场（双向，不限顺序）
ACK 确认达成一致 → 对齐完成
```

- 谁发起，向谁握手（方向由发起方决定）；有分歧就握手，无快速通道（通道会被滥用）

### 交付链（交付对象与验收分工）

- **后端/客户端交付对象 = 只有 Arch**：后端/客户端完成 → 直接交 Arch（评审/验收），不经 QA/PM
- **Arch 验收通过后**，再交付 QA 与 PM：
- **QA = 跑测试**（验收执行/测试验证）
- **PM = 一行一行细致 code review**（覆盖后端/客户端与 Arch 写的代码——源码与测试均在 review 范围）
- 交付链串行：Arch 未通过不进入 QA/PM 环节；团队链上留痕（评审意见/测试结果/code review 结论均归口 PM 发布）

### 交付对抗协议（2026-08-06 苍蓝星指示：交付时就要有对抗与阻力，不能顺利交付）

**分角色立场（2026-08-08 苍蓝星定）**：PM/QA = 业务一方（用户价值/验收标准/业务场景立场），Arch/后端/客户端 = 技术一方（可行性/成本/实现立场）——双方既有合作（共同交付）也有对抗（互相质询）；对抗是常态分工不是找茬。业务方质询技术方案问「业务影响是什么」，技术方挑战业务要求给「技术成本/风险 + 替代方案」；对抗收敛 = 摆证据、团队讨论、User 拍板（#144 方案 a 完整示范：业务方指业务损失 → 技术方评估契约成本 → 团队收敛 → User 定案）。

**总则：交付 = 进入对抗流程而非宣告——默认不通过，证明才放行；四关各自产出「阻力证据」才可放行，无阻力证据的关卡 = 未完成。**

1. **交付方自对抗**：宣布完成必附对抗材料 = 自查证据（tsc/定向测试/残留 grep/边界用例）+ **已知弱点声明**（3 个最可能被挑战的点：未验证边界、可能反例、妥协点）；自查不齐或未做门槛检查 = 交付无效打回
2. **交付门槛检查（M2 教训转门槛）**：残留扫描类检查（如旧信封 grep = 0）强制进交付门槛——tsc 清零 ≠ 正确，wire 形状靠 codec/集成钉测与残留扫描
3. **Arch 评审 devil's advocate**：先假设有错再找证伪证据；阻断级意见 = 打回重做（无「有条件通过」）；B 级 = 执行方当场表态采纳/不采纳 + 理由；评审结论附可证伪路径（哪一步可推翻，对抗不单向）
4. **QA 验收对抗场景**：验收必含 ≥1 个对抗性构造（异常输入/边界/并发/破坏性路径）；QA 交证据前 Arch 核证据本身
5. **PM 逐行 review**：存疑点不因验收通过而跳过；交付方弱点自曝清单是 review 靶子
6. **对抗模式库**：实证缺陷模式固化在 docs/architecture/adr/architecture-optimization-backlog.md「对抗模式库」节，交付对抗时红队/评审按清单逐项攻击，随真实缺陷追加
7. **补充通道（反驳权）**：评审意见后 1 个 commit 周期内可反驳，反证据须具体（对照/复现/数据），过期视为接受；Arch 复核维持原判或升级 PM 裁决

### 交付交互：四次挥手（固定 4 条消息，无快速通道）

```text
FIN 执行方 → 验收方：完成声明 + 证据
ACK 验收方 → 执行方：收到证据
FIN 验收方 → 执行方：验收结论（通过/有问题）
ACK 执行方 → 验收方：确认 → 交付关闭
```

- 谁交付，向谁挥手（方向由发起方决定）
- **粒度：仅可验收节点走挥手**（有验收人、有验收条目）；中间产物（commit、草稿、临时适配）不算交付，靠群聊正常流转

### 分歧裁决线（User 批准）

- **文档/需求分歧 → PM 裁决**；**技术/契约分歧 → Arch 裁决**
- Arch 的架构产出必须以文档形式提交 PM 裁决
- 实现落地触发的既有测试适配：**Arch + PM 裁决，QA/后端/客户端提供意见**

## 5.5 第一性原理规则（思维方法，全员适用；2026-08-08 苍蓝星指示固化，随 #123 批次生效）

> 调研来源：Addy Osmani《First Principles for Software Engineers》（分解→质疑→重建四步法 + 自查四问）、Forgeplan FPF（decompose/evaluate 推理模式 + 决策记录可审计）、Aviv Ben-Yosef《First-Principles Debugging》（诊断性提问）、ITNEXT《First Principles Thinking In Software Development》（假设是自摆乌龙）。

**定义**：任何决策/方案/判断，先回到「不依赖假设就为真」的根本事实（first basis），再向上推理；禁止以「类比/惯例/大家这么做」作为决策理由。类比只作假设来源，不作依据。

### 触发场景（门槛：至少满足其一）

- 决策不可逆或影响面大（契约变更/范围裁决/架构选型）；
- 存在分歧（两方以上立场冲突）；
- 模糊或新领域（无先例可循）；
- 复杂问题（多次返工/反复修不好）。

**不触发**：日常低风险、可逆、有默认值的事按 §6 默认值直接走，不逐项拆解（防滥用；Forgeplan 原则：答案明显且可逆时跳过繁文缛节）。

### 操作四步（任何决策/评审/调试前过一遍，必要时口头留痕）

1. **识别问题**：定义要解决的真问题（不是表面症状）；问「用户/系统真正需要什么」而非「现状哪里别扭」。
2. **分解到基本单元**：把问题拆到不可再分的根本事实（系统不变式、协议契约、已证实的物理/逻辑事实）；每层追问「这个断言还能再拆吗，它依据什么」。
3. **质疑假设**：把推理中每条假设标注来源——事实（已证实）/ 惯例（大家都这样）/ 猜测（未验证）；**惯例与猜测级假设必须给可证伪判据**，否则不得作为决策支点。
4. **重建与验证**：从根本事实向上推导方案；方案附「若哪条假设不成立则方案失效」的脆弱点声明（与交付对抗自曝弱点同源）。

### 反模式（禁止，评审/评审意见中直接指出）

- **类比决策**：「X 用了 Y 所以我们也用 Y」「业界标准是 Z 所以必须 Z」——类比只可作假设来源，作依据即违规（Osmani 核心警告）；
- **假设当事实**：把「应该是这样」说成「就是这样」——与 §8 症状≠根因同源；
- **惯例辩护**：「以前一直这样」作为理由——惯例要经受「当初的假设现在是否仍为真」检验；
- **结论先行**：先有答案再找论据——先出结论后补理由的论证一律退回重述。

### 自查四问（决策/评审/交付宣布前，向自己或对方提问）

1. 我怎么知道这是真的？（证据来源是什么，还是推论/惯例/猜测？）
2. 这个断言拆到最底层了吗？（中间层假设被当作根本事实了吗？）
3. 相反的证据或视角是什么？（主动证伪，至少想一个推翻它的构造）
4. 如果这条假设不成立，方案/决策还成立吗？（依赖脆弱性）

### 角色应用映射（各角色主职落地）

- **PM**：需求分析先问本质——「为什么做/为什么不做/做到什么程度算完成」从需求本质推导验收标准，不堆砌惯例功能；范围裁决时对「别人都这么干」类理由按反模式拒绝；
- **Arch**：方案与契约评审从系统不变式/协议契约推导；对惯例选型（「行业都用 X」）主动提问其成立前提；ADR 记录决策依据（决策记录可审计，FPF 同源）；
- **后端/客户端**：实现前问「该行为的最简正确形态是什么」；调试用 5 Whys 追到根因（§8 同源：相关≠因果，受控复现才可宣布根因）；
- **QA**：断言有效性质疑——「测试测到的是不是真的目标行为」（#83 J4 四轮假绿教训：测试通过≠测到目标，红基线必跑）。

### 与既有规则的关系

本规则是思维底座：§8 症状≠根因、契约零漂移（协议是已证实契约，改动须团队确认）、验收驱动（标准可验证才成立）、交付对抗（自曝弱点 = 脆弱点声明）均为本规则的具体实例；发生冲突时本规则优先（它约束的是论证方式，不改变职责与流程）。

## 6. 默认值（减少往返）

### 引用状态的时间戳约定（Arch 建议、QA 请求落文、PM 采纳）
- 引用 GitHub issue 一律带 updated_at 时间戳（如「引用 09:20:01Z 版」）；质疑「已改/未改」先报自己读的版本
- PM 每次更新 issue 后播报时间戳；以 GitHub API 正文 updated_at 为准（GitHub 页面/群聊消息转述都可能滞后）
- 版本交叉时以 curl/API 直读值为权威，不反复争论（#114 讨论中旧快照误判多次发生，此约定防再犯）

### 接力棒发言协议（接棒机制让所有流程都支持，防混乱——替代原「讨论顺序协议/主棒制/多棒并行」表述，统一为单棒制）
1. **版本锚前置**：任何引用 issue/文档的发言先报自己的读取版本（updated_at/commit hash）；无版本锚的引用视为无效，不进入讨论
2. **单棒制（所有流程统一）**：任一时刻**仅持棒者发言**；发言末尾显式递棒（「棒→X」）；持棒者完成议题必须递棒（不悬挂、不冷场）；非持棒者**不说话**（不插话、不抢答、不确认复读）——适用于一切群聊流程：讨论、头脑风暴、验收、落盘播报、状态汇报
3. **User 特权**：User 可随时接棒、指定接棒者、插话（主持人特权，不受棒制约束）；User 的指示 = 最高优先，视为即时递棒
4. **工作线并行（§7.5 保留）**：后台工作线可并行推进（实现/验收准备/评审预审），但**群聊发言权仍单棒**——线内需要发言时按棒序传棒；一角色同时只持一棒
5. **异常豁免**：§7.7 异常报告（非预期红/环境异常/卡点）**发现即报不受棒制限制**，但报完即静默（不展开讨论，讨论按棒序）
6. **已定案不重议**：同一议题三方确认一致即关闭；再议需新论据（事实增量，复述不算）
7. **一轮一议题**：发言聚焦当前议题，不夹带其他议题（夹带内容下轮再议）

- 默认落点：PM 指定分支（跟随 issue）；main 不动
- 默认只读：讨论阶段不写文件、不写 issue（本地临时记录）
- 默认范围：User 没提的不做；"其他不动"严格执行
- 默认署名：无需强制【角色名】开头
- 默认提交：一个逻辑一个 commit；各角色产出属主文件改动到工作区（不自行 git add/commit），由 PM 统一检查并落盘；禁 `git add -A`

## 7. 任务状态流转与汇报

讨论收敛 → User 批准 → 开 issue（PM）→ 布置 → 回读确认 → 分支开发 → 开 PR（附五要素 + 验收证据）→ 评审/验收（Arch/QA，PR 留痕；按验证阶梯引用证据，不重跑全链）→ User 合并 → **QA 在 main 验证（树相等核对 + 引用 PR 门禁证据，不重跑全量；命令 + 结果留痕；User 已更新本机 pi 至最新 pi-tavern 并实测）** → 关闭 issue（main 验证通过 + User 确认）

**状态汇报归 PM**：PM 向 User 汇报任务状态（卡点、等谁、下一步）；其他角色通过群聊与 PM 对接，不直接向 User 汇报；User 可看群聊讨论。状态在群聊声明 + issue 评论区登记（PM 属主，状态变更须群聊确认）。

### 验证留痕与分级验证（v0.4→v0.6，验证不要重复跑；**v0.6 超驰注记：门禁改分层压缩默认定向、全量 test:qa 按需触发——见 V1 触发条件 ①-④**，本节其余 v0.4 内容不变）

**验证分类（控制论优化，2026-08-06 苍蓝星点头）**：
- **验证锚**（红→绿闭环 / --omit=dev 实证 / 验收门禁）：保留独立双证——互证两次发现真问题（typebox 双列、旧信封 4 处残留），发现价值 > 成本
- **常规状态确认**（lint:layers / 基线绿 / grep 残留）：引用留痕不重跑，单点执行（同层同套件同状态只跑一次）

**核心原则：同一状态（同 hash + 同层 + 同套件）只验证一次；留痕即证据，引用不重跑。**

**默认不跑（v1.3**：任何验证动作必须先显式声明「跑什么」——命令必须含目标（文件/套件/定向），**不隐式跑全量或大面**；默认行为 = 不跑。验证声明格式：`npx vitest --run --config <层配置> <目标路径/定向>` + 理由（对应改动面）。全量触发条件（收窄）：① 收口门禁（里程碑/PR 收口）② 契约变更（影响面声明=全链）③ User 要求 ④ QA 判定（交叉核对后扩散超出定向能力）。定向原则：只跑改动涉及文件（unit 受影响文件 / integration 受影响套件 / acceptance 受影响文件——按 V2 影响面判定）

- **V0 证据格式与四级锚定**：每次测试运行在 PR/issue 评论区留痕一行「命令 | 结果摘要 | hash@层 | 环境」（层 = unit / integration / acceptance / 全量；环境分两类锚，不可混用——① 验收门禁锚 = references/pi@子模块 commit + node 版本（acceptance 经 pi-test.sh 驱动子模块内真实 pi，当前 5bc1c2c0）；② 真实环境锚 = 全局 pi 版本 + node（User 实测 / main 验证）。acceptance 证据必须含门禁锚；跨类引用 = 环境漂移 → 重跑受影响层；references/pi 子模块升级（User 日常更新）即触发；子模块 pin 与全局版本的已知差异属后端/客户端/PM 协调项）；未留痕视为未发生；引用写「引用 <hash> 证据」。hash 锚定分四级：
- ① 自测/红测（常含未提交改动，PM 落盘前）：标注「含未提交改动，基线 HEAD=<hash>」——仅参考/测试有效性证明（证明测试钉住缺陷），不作权威证据、不可引用
- ② 权威锚 = PR 门禁分支头（committed tree）：QA 在分支头跑门禁那一刻的树（默认定向、按需全量，见 V1），是唯一可引用锚；跑启动时记 HEAD，运行中分支头前进则该证据对新头过期——补跑或标注 delta
- ③ 同树引用：已提交树上的绿跑（main 验证树相等核对）可直接引用
- ④ 变更重跑触发：分支新提交 / 环境漂移 → 重跑受影响层后再锚
- 脏工作区陷阱：HEAD 不含被测内容时禁止裸引用 hash（会锚到错误树 = 引用无效证据，恰是本规则要根除的）
- **V1 分级验证阶梯**（非全链默认）：
- 红测链（QA）：只跑新增/受影响测试文件证红，留痕标注失败阶段（哪个 waitFor/断言、多少秒超时），后端/客户端据此直指修复点，避免二次排查；红测定位 = 测试有效性证明，非权威证据（V0-①）
-后端/客户端自测（分工：**后端/客户端跑单元测试，Arch 跑集成测试，QA 跑 acceptance 及以上**；**后端/客户端可跑集成测试，不怎么耗时**）：unit 受影响层 + 红测转绿目标文件（unit 域）+ **integration 可跑**（秒级 ~13s，成本可忽略，放宽）；证绿时反向引用对应红测（「对应 Arch/QA 红测 <hash> 失败阶段 X，已修复，现绿」+ 修复点文件/机制），红绿两行证据互相锚定，评审一眼看出红在何处/改在何处/为何转绿。**后端/客户端不跑 acceptance 全量**（验收层证据 = QA 域，后端/客户端多跑 = 重复根源之一）；后端/客户端需要验收层行为确认时声明由 QA 执行或等验收
- 评审（Arch/QA）：diff 审查 + 只跑被改动文件的 unit 抽查，不重跑全链。**评审线（Arch 承担 code review）**：Arch = 架构/契约评审 + **代码评审**（代码正确性、边界与错误处理、命名与可读性、测试充分性——对后端/客户端每步落盘 commit 与 PR 终态均适用）；QA = 测试质量与验收证据评审（断言覆盖、红绿锚定、验收口径）。后端/客户端响应评审意见（L42 GitHub 分工），评审意见由 PM 归口发布到 PR/issue。**评审风格从严（Arch 加严、代码洁癖）**：死代码/重复实现/命名/可读性/未简化结构一律指出（区分阻断/B 级），「干净」是合入前提，小瑕疵随发现随修落盘，不留里程碑
- **默认门禁 = 分层压缩（v0.6，不默认全量，QA 只跑改动的，等需要时跑全量）**：unit 全量 + integration 全量（秒级 ~13s，成本可忽略不裁）+ acceptance **只跑受影响文件**（定向，范围按 V2 影响面判定）。**全量 test:qa 按需触发**，触发条件（任一）：① 契约面变更（协议/持久化/schema/ADR，影响面声明=全链）② User 要求 ③ QA 判定（声明与 diff 交叉核对后影响面扩散超出定向能力，或周期性校准防盲区累积——如每 5 个 PR 择机一次）④ 关闭 issue 收口时 QA 判定需要。门禁执行细节：跑前 `git status` + `git rev-parse HEAD` 确认分支头且工作区干净（脏树不跑门禁，杜绝权威锚锚到脏树）；定向跑留痕附受影响文件清单 + HEAD^{tree}，全量跑留痕同 V0。后端/客户端协调承诺：QA 宣布跑门禁时后端/客户端不产出新改动；在途产出先交 PM 落盘或明示 QA 延后门禁
- **V2 双因子重跑判定**：重跑触发 = ① 涉及文件变更（src/test/docs）→ 重跑受影响层；或 ② 影响面声明——**实现者随证据链自带「影响面」字段**：受影响层小枚举（unit / acceptance-定向(附用例名) / 全链）+ 一句理由（如「改动拉取等待窗口 → 须重跑 live-delivery」）。**QA 判定 = 实现者声明 + 只读 diff 交叉核对**（重点扫异步/定时/超时/轮询类改动，秒级成本；声明是断言非证明）。声明与 diff 不符时才要求补跑；无触发 → 引用旧证据。
- **V3 证据复用与树相等**：同 hash 直接引用；main 验证 = `git rev-parse main^{tree} == PR头^{tree}` 树相等核对 + 引用 PR 门禁证据 + User 实测（真实环境），不重跑全量；树不等（合并冲突解决）才重跑受影响层。树相等只证内容相同、不证环境相同——引用时对照证据行环境上下文（pi 版本号），环境漂移则重跑受影响层。**逐 PR 验收同规则（User 批评「重复跑测试」后补充）**：QA 逐 PR 验收 = 树相等核对（HEAD^{tree} == 实现者证据对应 tree）+ 引用实现者证据 + 仅新增/受影响用例定向抽查；**不重跑实现者已跑过的同层同套件**（同状态同层同套件多次运行 = 重复，V4）。全量重跑仅限：收口门禁（攒批最终证据）/ 契约面变更 / User 要求 / QA 判定影响面扩散（v0.6 触发条件）
- **V4 红/绿状态区分**：QA 证红与后端/客户端证绿是不同状态，各跑一次不算重复；重复指同状态同层同套件多次运行。
- **V5 与 #45 分工**：本规则消「重复跑」（次数维度）；#45 优化单次成本（耗时/CPU），排期不受本规则影响。
- **实验方法铁律（v0.6 补，QA 教训 #52）**：A/B 对照必须配对——同时刻交替 ≥3 轮取稳定值；单次/异时对照会被环境漂移污染（实证：假 key「12.4s vs >150s」为群聊高峰/网络异常伪差，真值 23-26s 无差）。结论入档前先审配对性。

## 7.5 并发协作（v1.0，后端/客户端干活时 Arch/QA 不应干等，工作流应支持并发）

**核心原则：等待只发生在真实依赖边——谁依赖谁的产出就等谁；不依赖的并行准备。串行阶段（评审/验收等后端/客户端终态）是反模式，用「前置产物 + 阶段重叠 + 增量审计」消除。**

1. **前置产物先行（三线并行起点）**：
-后端/客户端开工前，Arch 完成方案/契约评审（结构先定，实现不再等评审）；契约面（协议/持久化/schema）定稿即发 QA
- 契约先行 → QA **红钉先行**：测试钉住契约，不等实现（红钉 = V0-① 自测证据，实现落盘后转绿锚定）
- PM：范围/验收锚点在 Task Brief 先定，不拖到验收时
2. **实现期间（后端/客户端主跑，Arch/QA 并行准备自己的属主产出）**：
- Arch：增量审计（依赖方向/契约面）——对后端/客户端**每步落盘 commit** 进行，不阻塞后端/客户端后续步；发现接缝问题给「输入」而非「关卡」
- QA：写测试钉（红钉先行）、预跑既有套件增量回归（对每步落盘态）、验收清单预写——全部在 test/ 属主域内
- 交叉产出互不阻塞：后端/客户端不停步等 Arch/QA 中间结论；Arch/QA 中间结论作为后端/客户端输入随时吸收
3. **阶段重叠（流水线）**：阶段 N 验收（QA 门禁）与阶段 N+1 方案设计（后端/客户端/Arch）并行；阶段 N+1 红钉（QA）与阶段 N 收尾（后端/客户端）并行
4. **门禁并发约束（防假并发）**：QA 宣布跑门禁时后端/客户端不产出新改动（既有承诺保持）；在途产出先交 PM 落盘或明示 QA 延后；权威锚纪律不变（V0-② 只有落盘 commit 态可锚）；并发 = 各方在属主域内准备，不交叉抢改（src=后端/客户端/ test=QA / adr=Arch / 计划文档=PM）
5. **汇报节奏**：每步报告附「下一步可并行启动项」（如后端/客户端报告下一步 X → Arch/QA 据此启动并行准备，不等完成通知）
6. **预跑窗口（v1.2，教训：37d1b74 落盘后 integration 52 红）**：大拆解/装配重构类任务，PM 落盘前与 QA 协调预跑窗口——QA 对工作区 WIP 态预跑 integration（脏树预跑 = V0-① 参考证据，绿灯才落盘为权威锚 V0-②），防止中间态落盘为不可锚 commit；unit 绿不覆盖 WS 集成面，后端/客户端声明「unit 全绿」不等于 integration 可锚；落盘仅凭 unit 绿 = 违规风险
6.5 **落盘文件清单核对（v1.3，教训：2b0d723 误含 QA family 中间态）**：PM 落盘前 `git status` 文件集与本次声明范围**逐项比对**——清单外文件一律不落（属主在途中间态隔离在声明外）；禁 `git add -A` 盲落；与预跑窗口互补：预跑验内容、清单验边界，双保险
7. **acceptance 孤儿进程清理（v1.2，QA 固化）**：跑 acceptance 前 global-setup 自动 killOrphanedPiProcesses（pkill 仅匹配本仓 references/pi/pi-test.sh 路径，项目作用域不误杀）——历史孤儿进程会让全量 >600s 卡死，此清理已固化；测试改游标断言时同步核对实现路径（#71 遗留教训：legacy 路径读者漏同步）

## 7.6 协作机制（v1.4，风暴收敛：「PM 要总是收尾」）

**总则：PM 是总收尾者**——主动收敛、关闭、推动，不让事项悬挂（决策点给默认方案、审批点批量请求、分歧点及时裁决）；各角色配合收尾（动手前自查、状态不重复播报）。

1. **状态真相唯一化**：状态以 git log/工作区为准，消息仅作声明与裁决——动手前自查三连（`git branch --show-current` + `git status` + `git log --oneline -3`）；PM 落盘后发 commit 索引，不逐条确认；同一事实只发一次（免补发）
2. **分工矩阵**（开单即定主辅，不再逐案讨论）：钉测类 = QA 主（integration/acceptance）+ Arch 主 unit 层；实现/基建类 =后端/客户端；文档/纪律类 = PM 主 + 属主出内容；评审/调研类 = Arch。每 issue 一条关键路径（串行瓶颈）+ 其余角色**并行预研**（评审预判/方案草案/测试设计），不空转不抢改（#85 教训：修复选型可前置预研）
3. **等待窗口显式化**：等待真实依赖（审批/数据/合并）期间，声明可并行项（不依赖远端/不占验收层资源的产出）；PM 排程优先填充空档
4. **钉测即验收模式**：修复类 issue 默认将验收条目拆为可钉测断言（钉测 ↔ 修复一一对应）；可钉测化是准入条件——拆分时先问「能否转可钉测断言」（QA 把关），不可钉测面（TUI 视觉/真实 LLM 行为）才走人工验收，端到端烟雾为兜底模板
5. **PM 收尾动作**：落盘攒批（约 15 分钟粒度 + commit 索引播报，不逐条）；验收条目由验收方起草 PM 审；风暴/讨论收敛后立即给默认执行方案，User 可喊停单项
6. **验收两级制（试点，QA/Arch 把关条件）**：后端/客户端/Arch 自验（红绿 + 留痕）+ QA 终验——「关键面清单」（契约面/门禁面/持久化面必全验，QA 起草 Arch 审）内全验，抽验仅限低风险常规批次；V0 留痕纪律不降级（每批仍留命令|结果|hash）
6.5 **风暴自动收敛（控制论优化）**：风暴 15 分钟无实质增量 → PM 整理收敛稿（共识/分歧/下一步）交 User；User 可随时喊停不变——防 User 离开时风暴悬挂（收敛仍归 User，PM 只做整理不代拍板）
7. **前馈闭环（控制论优化，2026-08-06 苍蓝星点头）**：每里程碑验收时 Arch 对照开工盘点（分工建议表）回注「预估 vs 实际」偏差（人日/文件数）——偏差回注下轮开工盘点，形成闭环；S/M/L 声明从开环预估变闭环校正
8. **双环回顾（控制论优化）**：每里程碑收口附 5 分钟流程回顾（「哪些规则该改」）——单环纠偏之外的双环学习，产出进架构优化待办清单；不单独开会，随验收播报一句话即可
9. **测试分层下沉（与 #92 联动）**：仅「#52 等价条件」场景（进程内可等价验证）可 acceptance → integration；真实 pi 进程 e2e 覆盖不牺牲；下沉清单 Arch 按 #52 逐项把关
10. **双 worktree（声明制）**：并发任务经声明可双开（属主/任务/目录入 issue）；node_modules 可链接共享；**验收/门禁错峰**——QA 宣布跑门禁时另一线停 acceptance（run-tests 端口/临时目录/pkill 作用域共享，#52 铁律）；收口随分支清理
11. **红线不动**：git 写操作归 PM（分层不做）、验证默认不跑、契约零漂移、push/merge/PR 归 PM——**推送审批保留逐次（pi 需要审批推送步骤，不做批量授权）**

## 7.7 异常报告流程（v1.5，不能总是一个人闷头做）

**总则：发现即报，禁止「查清再报」**——先报现象 + 影响，排查过程边做边报；团队知情优先于个人查清（W1-c 教训：PM 闷头查三轮环境问题才报群）。

1. **触发条件（以下必报）**：
- 非预期测试红（钉测红 = 预期，不报；回归红 = 必报）
- 环境异常（子模块缺失 / 端口冲突 / 进程卡死 / 工具缺失 / 路径不通）
- 计划偏差（分支基点错 / 方案偏离 / 范围变化 / 属主越界）
- 卡点（等审批 / 数据 / 依赖超预期、任务受阻）
- 实验异常（基准数据跑飞、与基线差超预期、参数不受控）
2. **报告格式**：现象（一句话）+ 影响（谁受影响）+ 已确认事实（证据/日志/命令）+ 求助项（要谁做什么）；必要时附最小复现
3. **闭环**：报群 → 团队知情 → 相关角色认领 → 定案（修复 / 降级 / 挂起）→ 结果回报；无人认领 PM 兜底裁决
4. **例外**：无——纯本地实验数据异常同样必报（数据是共享决策输入，如 #92 基准）
5. **与 §8 关系**：本流程是上游（发现即报），§8 Bug 排查是下游（根因深挖）——报告先行，排查跟随
6. **测试失败即时报告（2026-08-08 苍蓝星指示：验收时 bug 提交群聊太慢，每次测试跑不通就报告）**：任何测试运行——**每次跑完即报**（无论绿/红/挂起：命令 | 结果摘要 | 失败点/根因线索 | 下一步），挂起/环境异常**发现即报**（不静默重试），定位类工作**分段播报**（每轮实验或最长 15 分钟一报：假设/证据/结论），收口门禁**每层一报**（unit → integration → acceptance → check → lint:layers，失败立即附红测证据）；红钉预期红不在报列（流程内预期）；PM 对测试失败报告**及时响应**（认领/协调/兜底），不静默（#123 it1 埋头定位 30 分钟未播报教训）。**输出落盘防截断（2026-08-08 QA 修正）**：跑测试输出重定向落盘（如 `2>&1 | tee /tmp/run.log`），失败时从完整日志提取「Failed Tests」段（用例名+断言+行号），不依赖 tail 汇总——汇总行不携带失败详情。**bug 报告业务场景化（2026-08-08 苍蓝星指示）**：QA 提交 bug 以业务场景为先——报告格式 = 「谁、在什么场景、会怎样」（业务语言，期望表现 vs 实际表现），技术细节（复现步骤/断言/日志/代码路径）作证据附后；同一问题先业务后技术（#144 T2 首例示范：「角色刚进群就有人发言，这条消息永远看不到」）
7. **发现问题 ≠ 定位问题（2026-08-08 苍蓝星指示：定位不应该由 QA 处理，应该大家一起处理）**：QA 的职责止于**发现与报告**（现象 + 证据 + 影响面，疑似面可标注但非结论）——报告后即转交，**不独自闷头定位**；定位由相关域开发角色认领（后端/客户端按域、Arch 提供机制分析支持），QA 提供复现证据与验证配合，所有相关方共享定位过程（复现→假设→验证→定案，分段播报）；无人认领时 PM 派发或兜底。

## 7.8 架构优化点内嵌机制（苍蓝星指示：架构优化点不单独开 issue，在 Arch 设计方案时一并处理）

**总则：小粒度架构优化点走「登记 → 设计方案内嵌」通道，不单独开 issue；设计方案必须过一遍待办清单。**

1. **登记**：Arch（及各方）日常发现的小粒度架构优化点（非契约变更、非独立交付物、不达 issue 规模的）→ 登记到 `docs/architecture/adr/architecture-optimization-backlog.md`（Arch 属主，格式：优化点 / 发现背景 / 建议方案 / 状态）——**发现即登，随所在分支/PR 同批合入，不为 backlog 单独开 PR**（2026-08-08 苍蓝星拍板），不丢不烂
2. **内嵌（设计方案时）**：Arch 每次设计/评审方案（里程碑开工、契约变更、重构规划）时**必须扫描待办清单**：相关优化点并入方案设计，随方案实现一并落地（随 M 落盘，不留待办悬挂）；不采纳的显式记录理由（写入方案或清单状态列）
3. **边界**：以下仍走正常 issue 流程——契约变更（协议/持久化/schema）、独立交付物（新工具/新能力）、跨里程碑规划（如 0.3.0 roadmap）；规模判断归 Arch，拿不准问 PM
4. **勾销**：优化点随方案落地后，Arch 在清单勾销（注明随哪个 commit/里程碑落地）；清单是活文档，PM 排期不为其单独开 issue
5. **验收锚**：设计方案输出附「待办清单核对」段（本次扫描结果：并入项 + 未并入项及理由）
6. **顺手优化扫描（2026-08-08 苍蓝星指示固化：总要看可以顺手做的优化）**：Arch 在**每次批次归口时**（PM 布置/范围追加即触发，不等到收口）主动扫描待办清单，按「同文件/同域碰触 + 零行为变化 + 低风险」筛选可顺手项，输出候选交 PM 归口（并入当前批次或另排，PM 裁决）；批次收口前复核扫描结果（顺手项 + 不顺手项及理由随收口播报，不留静默区）。批内不采用 = 显式记录理由；待办悬挂由 PM 排期兜底

## 8. Bug 排查流程（v0.1，新增）

> 调研来源（网络检索）：Toyota 5 Whys（丰田生产系统）、Claude Code Engineering Playbook（Bug Hunting and Root-Cause Analysis）、REDUCE 调试框架（dev.to/matthewhou）、Sagy RCA Workflow（症状/证据/假设/验证分离）、diagnosing-bugs skill（反馈回路）、Astro triage（report 留痕闭环）、AI Bug Triage（不发明根因，证据可复核）。

### 核心原则（来自调研，本次 #83 教训对应）

1. **复现先行**：先拿到可复现的最小步骤，再谈假设——「反馈回路」是调试的唯一关键技能（diagnosing-bugs Phase 1）
2. **症状 ≠ 根因**：把「像什么」当「是什么」是最大失败模式；从「看到症状」直接跳到「改了什么症状停了」不是修复，是巧合（Claude Playbook）
3. **相关 ≠ 因果**：时序吻合只是候选证据；宣布根因前必须受控复现或 ≥2 条独立实证链（#83 教训：两次 reset 与掉线时刻吻合即宣布，被 User 质疑合理）
4. **5 Whys**：每个「为什么」的答案都是下一个「为什么」的输入，直到落在可行动的流程缺口/缺失护栏上（Toyota）
5. **证据可复核**：结论必须附「另一个工程师能复核的证据」，不凭模型/印象断言（AI Triage）
6. **留痕闭环**：无论结论如何（含未复现/无结论）都要写 report，不静默（Astro）
7. **修复钉测**：回归测试先红后绿，钉死在旧代码失败/新代码通过的形态（Playbook）

### S0：症状卡（PM 采访 User，进 issue 才开查）

5W1H 模板，缺项标注「待补」不阻塞开查：
- **操作时间线**：问题前后 User 做了什么（更新/重启/配置/部署）——#83 最大教训：User「更新 pi-tavern 后才出问题」是最快线索，第一轮就该采到
- **现象**：精确描述（看到了什么/没看到什么/哪个界面）
- **时刻与频率**：首次/最近一次/一次性还是反复
- **影响面**：全体 vs 单个（#83 补充：其他角色是否同时异常——区分机制面与会话面）
- **恢复动作**：怎么恢复的（重启/重连/等自动恢复）（#83 补充）
- **会话与终端**：哪个角色/宿主/TUI
- **日志与报错**：原文粘贴（终端/会话文件/扩展错误）
- **期望行为**：本来应该怎样

### S1：环境快照（统一协议，git 证据必带仓库路径）

- **加载源**：`~/.pi/agent/settings.json` packages 钉（git:...@commit）+ clone HEAD/reflog（`~/.pi/agent/git/...`）
- **进程清单**：pid / 启动时刻 / 加载路径（`/proc/PID/cwd`、`ps lstart`）
- **版本矩阵**：运行时 pi（linuxbrew 全局）/ 测试锚定 pi（references 子模块）/ 扩展 HEAD——**三者不一致 = 门禁级关注项**（#48 A5 漂移教训）
- **仓库路径声明**：凡引用 reflog/git 状态必须写明是哪个仓库（dev 仓库 vs 扩展 clone）——#83 三轮回合拉扯的根因
- **会话文件识别用身份锚**：引用 ~/.pi/agent/sessions/ 的会话 JSONL 前，先用 custom_message 首行「你的当前角色：X」确认文件属主，不得凭内容推断（#83 教训：后端/客户端误用 Arch 会话文件反驳 QA 实证，后公开更正）
- 产出：快照附时间戳入 issue，作为后续所有证据的基线

### S2：复现评估（QA 主导，决定路线）

- **可复现** → QA 红绿测试先行（最小复现 + 对照组），直接进 S5 修复验证
- **不可复现** → 观测增强（补日志/埋点）+ 假设分层（进 S3），并升级为观察项持续跟踪
- 评估结果入 issue 留痕（可复现性本身是结论的一部分）

### S3：假设循环（后端/客户端，Observe→Hypothesize→Experiment→Conclude 科学循环显式化）

- 每假设标注置信等级：**实证**（直接证据支撑）/ **相关未复现**（时序吻合但无受控验证）/ **推测**（代码推演/静态分析）
- 每假设附可证伪判据（J1-J3 形式：复现场景 + 断言 + 预期红绿），**主动证伪**——防「死磕错误方向」是 AI 排查第一大失败模式
- 「根因」一词保留给「已受控复现」或「≥2 条独立实证链」；否则称「候选根因」

### S4：根因门禁（PM 把关，宣布前必过）

- 宣布「根因」须：受控复现 或 ≥2 条独立实证链（如 reflog×2 + settings mtime + 错误栈 + 会话 JSONL 四源合流，#83 实证）
- 否则标注「**机制实证 + 相关吻合，未受控复现**」并排期受控复现（#83 现状口径）
- 复现不了 → 不宣布根因，按「操作风险/观测项」降级处理（#83：包更新改写 = 独立操作风险，非根因）
- **定案记录与显式作废（#83 教训：根因三连翻）**：定案记录 = 结论 + 时刻 + 责任人 + 证据链 seq 号（入 issue）；任何翻转须群聊**显式作废旧结论（引旧 seq）**，新旧结论不得并存；重要结论翻转同步在 issue 更新权威口径（避免落后方按旧结论发言）
- **结论-产出绑定清单（#83 教训：修复批次险些随旧口径丢失）**：每个根因定案登记关联的测试/修复文件清单（issue 内维护），收口时逐项核对——复用 PM 落盘清单核对机制（6.5），防「结论已翻、产出未跟」或「产出随旧口径丢弃」

### S5：修复 + 验证

- 修复 = 因果修复（fix the cause, not the symptom）
- 回归测试先红后绿（钉测：旧代码失败/新代码通过形态），定向 + 层内全量门禁
- 版本缺口补跑：运行时 pi ≠ 测试锚定 pi 时补跑受影响层（#83：0.83.0 验收面）
- **合入前 check 清零（#89 教训：无 CI 本地人工门禁，欠账累积）**：项目无 CI（无 .github/workflows），check 为本地人工门禁——每批合入 main 前 `npm run check` 全绿留痕（命令 | 结果 | hash@层），与定向测试绿、V0 留痕构成合入三件套；biome/TS 版本变更 → 全量 check 清零后再合
- **git hook 自动化提醒（#89 落地**：husky（devDependency ~2kB，prepare 自动安装）pre-push hook 跑 `npm run check`，非零拒绝推送（`.husky/pre-push` 版本化）。本质 = 纪律的自动化提醒，`--no-verify` 可绕过、仅对安装了 hook 的机器生效，不替代纪律；GitHub 云端无免费 pre-receive hook（仅 GHES 有，云版靠付费 Rulesets 或 CI 载体）
- **测试有效性检查（#83 教训：J4 四轮假绿）**：测试"通过" ≠ 测到目标——写钉测后强制失败演示（临时断言必然失败，确认测试真触达目标路径）+ **红基线必跑**（同测试在未修复版必须红，否则测试无效）；防类陷阱：schema 严格校验（additionalProperties:false 下带多余字段被静默丢弃）、mock 注册链路未真实接通

### S6：复盘收口

- 5 Whys 复盘：本次排查流程哪里断了（症状采集/环境声明/复现时序/证据解读）→ 改进项落本文档（自我修正闭环，#83 已沉淀：操作时间线首轮必采、身份锚、双源交叉、宣布门禁）
- issue 关闭前置：User 实测确认 + 根因置信等级标注留档

- 修订：群聊提议 → 团队确认 → PM 更新本文档（落分支提交）
